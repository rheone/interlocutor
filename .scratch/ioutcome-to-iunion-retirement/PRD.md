# PRD: Retire `IOutcome` as the response constraint; adopt `IUnion`; introduce arity 0 and arity 1

Status: **ready-for-agent**. Tracked as issues under `.scratch/ioutcome-to-iunion-retirement/issues/`.

**Recommended sequencing:** land after `.scratch/outcome-naming-and-arity-refactor/issues/08-rename-case-type-templates-to-t1-tn.md` (the `T1..TN` case-type-parameter rename). Not a hard technical dependency, but both touch `Interlocutor.CommonKernel/Outcome.cs` directly, and #08 is already `ready-for-agent` and unblocked - landing it first avoids rework on the same file.

## Problem Statement

Every handler response is constrained today by `where TResponse : IOutcome` - a zero-member, project-owned marker interface, repeated across roughly thirty constraint sites in `Interlocutor.Abstractions`, `Interlocutor.FluentValidation`, `Interlocutor.AspNetCore`, and `Interlocutor.DependencyInjection.Abstractions`. This duplicates a concept the C# language now ships natively: `System.Runtime.CompilerServices.IUnion`, the interface every compiler-generated `union` declaration already implements. Maintaining a project-owned marker for something the language already identifies is unnecessary surface area, and it's weaker than the language's own mechanism for hand-rolled custom response types - `DefaultOutcomeCaseRegistry` already recognizes any `IUnion` implementer generically, but a hand-rolled `IOutcome` implementer that isn't shaped like a union has no case constructor for that recognition to find, forcing a consumer to hand-register a factory/extractor for a shape that a real (even hand-written) union would get for free.

Separately, the non-generic `Outcome` (`Success | Failure`) bakes a privileged, universal success/failure judgment directly into a type's shape - exactly the assumption ADR-0022 already rejected at the value-classification level, just recurring here at the type-shape level: nothing about "zero payload" implies "there are exactly two things that can happen here." And there is no shipped shape at all for an operation that is genuinely infallible but still needs to carry exactly one payload value, forcing such an operation to declare a `TFailureResult` case that can never actually construct.

## Solution

- Replace `where TResponse : IOutcome` (and `where TResult : IOutcome`) with `where TResponse : System.Runtime.CompilerServices.IUnion` at every constraint site. Same compile-time guarantee - a type not marked `[Union]` (and not hand-implementing the interface) still fails to compile against the constraint - now backed by a real language feature instead of a project-owned one.
- `IOutcome` and `IOutcomeCase` are **not deleted**. `outcome-union-decoupling`'s issue 01 already made `IOutcomeCase`/`ActiveCaseType` emission an opt-in the generator gates on a union declaring `: IOutcome` - that mechanism is untouched and continues to serve its existing purpose (a union that wants the classification surface declares `: IOutcome`; one that doesn't, doesn't). What changes is narrower: `IOutcome` stops being *anyone's compile-time response constraint*. The shipped `Outcome`/`Outcome<T1..TN>` family keeps declaring `: IOutcome` (to keep its classification surface); a hand-rolled custom response type needs only `IUnion` to be legal as a `TResponse`, and may additionally implement `IOutcomeCase` by hand if it wants the same surface.
- Introduce three genuinely distinct arities in `Interlocutor.CommonKernel`, replacing today's implicit two-tier model:
  - **Arity 0** - `Outcome`: a pure fire-and-forget acknowledgment. No case types, no payload, no success/failure judgment of any kind. Retires today's hardcoded `Success | Failure` shape. Usable only by a request that is genuinely infallible and opts into none of `ICancellable`/`IHasTimeout`/`IRateLimited` (none of those pipeline behaviors has a case to construct into a case-less type via `IOutcomeCaseRegistry.Construct`).
  - **Arity 1** - `Outcome<T>`: a single, always-succeeding payload wrapper. Hand-written, not generator-emitted (see Implementation Decisions), but exposes the same member shape as every other arity so a caller never special-cases it.
  - **Arity 2 to 16** - `Outcome<T1, ..., TN>`: unchanged in mechanism from today's `Outcome<TSuccessResult, ...>` family (that rename is #08's job, not this PRD's), a real generator-emitted discriminated union. No privileged, pre-baked `Outcome<Success, Failure>` convenience shape ships - a developer choosing a binary outcome writes `Outcome<Success, Failure>` (or any other two case types) explicitly.

## User Stories

1. As a consumer declaring a handler response, I want the compiler to reject a bare DTO that isn't a real union, so that every response stays exhaustively pattern-matchable, exactly as it is guaranteed today.
2. As a consumer authoring a fully custom, hand-rolled response type, I want it recognized by `DefaultOutcomeCaseRegistry` with zero custom registration as long as it's a real `IUnion` implementer, so that I no longer have to hand-write a factory/extractor pair just because my type isn't generator-emitted.
3. As a maintainer of a pipeline behavior that needs to short-circuit with a specific case (`CancellationBehavior`, `TimeoutBehavior`, `RateLimitedBehavior`), I want the response-type constraint mismatch between "claims to be `IOutcome`" and "is actually `IUnion`-shaped" to become a compile error instead of a runtime `OutcomeCaseNotSupportedException`, so that a misconfigured response type is caught before it ships.
4. As a consumer with a void command that is genuinely infallible and opts into no cross-cutting short-circuiting behavior, I want to return a pure acknowledgment carrying no manufactured success/failure judgment, so my type signature doesn't claim a distinction that was never real.
5. As a consumer with an operation that always succeeds but still produces exactly one value, I want a single-payload wrapper that doesn't force me to name an unreachable failure case, so my response type accurately reflects what the operation can actually produce.
6. As a consumer using the new single-payload wrapper, I want the same `Value`/`Match`/`Switch`/`TryGetValue`/`ToString`/equality members every other arity has, so I never have to special-case arity 1 at a call site.
7. As a consumer choosing a binary (two-case) outcome, I want to name both case types myself, so that `Success`/`Failure` are two ordinary case types available to me, not a privileged, framework-blessed pairing.
8. As a consumer with an existing handler returning the old non-generic `Outcome` (`Success | Failure`) to report failure, I want a clear migration path (declare `Outcome<Success, Failure>` explicitly, or the appropriate richer arity for the failure modes actually produced), so upgrading doesn't leave my failure path silently unreachable.
9. As a maintainer of `documentation/`, I want every example built around the retired `Success | Failure` `Outcome` (the `ClearCache`/void-command worked examples throughout `messages-and-result-types.md`, `beginners-guide-todo-api.md`, and `TutorialProject`) updated to the new arity that actually matches each example's real failure modes, so the shipped docs keep compiling against the real API.
10. As a consumer reading `documentation/messages-and-result-types.md`'s arity guidance, I want the three arities' distinct roles (acknowledgment / infallible-single-value / real discrimination) explained plainly, so I pick the right one without guessing.
11. As a maintainer of `Interlocutor.Abstractions.Pipeline.Cases.IOutcomeCaseRegistry`, I want its own `where TResponse : IOutcome` constraints swapped to `IUnion` consistently with every other site, so there's exactly one governing constraint across the whole library, not two coexisting ones.

## Implementation Decisions

- Swap `where TResponse : IOutcome` / `where TResult : IOutcome` to `where TResponse : System.Runtime.CompilerServices.IUnion` / `where TResult : IUnion` at every site currently constraining on `IOutcome`, across `Interlocutor.Abstractions` (mediator core, handler contracts, all pipeline behaviors, `IOutcomeCaseRegistry` and its builder/default implementation, `Eject`/`NoCommit`/`PipelineEjectException`), `Interlocutor.FluentValidation` (`ValidationBehavior`, `FluentValidationErrorsBehavior`), `Interlocutor.AspNetCore` (`ResultExtensions`), and `Interlocutor.DependencyInjection.Abstractions` (`RootScopeGuardedMediator`).
- `IOutcome` and `IOutcomeCase` remain in `Interlocutor.CommonKernel.ResultTypes`, unchanged in shape and in the generator's existing `: IOutcome`-gates-classification-surface behavior. The shipped `Outcome`/`Outcome<T1..TN>` family keeps declaring `: IOutcome` alongside whatever base the `union` declaration syntax already gives it.
- Arity 0 (`Outcome`): a small, hand-written type (struct) - not generator-emitted, since it declares no case types at all. Implements `System.Runtime.CompilerServices.IUnion` directly (`Value` always returns `null`) purely to satisfy the `IUnion` constraint; holding an instance of the type is itself the acknowledgment, not anything read from `Value`. No `Match`/`Switch`/`TryGetValue` members - there is nothing to dispatch over.
- Arity 1 (`Outcome<T>`): a small, hand-written generic type - not routed through `OutcomeMemberGenerator`/`[GenerateOutcomeMembers]`. `INTERLOC011`'s existing floor of two case types is correct for a *consumer's* attributed union declaration (protects against an accidental, meaningless single-case union) and is left completely unchanged; it simply doesn't apply to this deliberately hand-written shipped type. `Outcome<T>` exposes: a strongly-typed public `T Value` property (not boxed); an explicit `object? System.Runtime.CompilerServices.IUnion.Value` implementation forwarding to it; `TResult Match<TResult>(Func<T, TResult> onValue)`; `void Switch(Action<T> onValue)`; `bool TryGetValue(out T value)` (always returns `true`); `ToString()` forwarding to `Value?.ToString()`; and the same value-equality shape as every other arity (`Equals`, `GetHashCode`, `IEquatable<Outcome<T>>`, `==`/`!=`, delegating to `Value`'s own equality).
- Arity 2 to 16: no mechanism change in this PRD - the `T1..TN` symmetric-naming rename is #08's scope, not this one's. This PRD's only touch on that family is removing any remaining implication (in doc prose or examples) that `Outcome<Success, Failure>` is a privileged or recommended default rather than one ordinary choice among many.
- `IOutcomeCaseRegistry.Construct<TResponse, TCase>`/`TryGetActiveCase<TResponse>` (and their builder/default implementations) move to the `IUnion` constraint along with everything else - `DefaultOutcomeCaseRegistry.TryGetActiveCase` already checks `response is IUnion` at runtime and throws `OutcomeCaseNotSupportedException` when that fails, so this specific swap converts an existing possible runtime throw into a compile error for the same misconfiguration.
- `documentation/messages-and-result-types.md` (`IOutcome Constraint`, `IOutcome as an Extension Point`, `Result Types`, `Outcome Unions`, `Variance` sections), `documentation/extensibility.md` (`IOutcome as an Extension Point`), `documentation/composing-outcome-arities.md`, and `documentation/glossary.md` (`IOutcome`, `Result Types` entries) are updated in the same iteration as the code change, per this project's documentation-maintenance convention - not deferred to a follow-up ticket.
- `CONTEXT.md`'s existing "Arity" entry (already settled during this design's grilling session) is the source of truth for the three-tier definition - extend it if implementation surfaces a term it doesn't yet cover, don't restate it differently.

## Testing Decisions

- Test external behavior: a response type that is `[Union]`-attributed but does not implement `IOutcome` still compiles and dispatches correctly through every pipeline behavior and through `IOutcomeCaseRegistry` - proving the constraint swap, not just the type-check, is complete.
- A response type implementing bare `IOutcome` but not `IUnion` must now fail to compile at every constraint site - a compile-time regression test (or a documented failing-build sample under the generator's existing diagnostic test conventions) proving the tightened guarantee from User Story 3.
- Arity 0 (`Outcome`): a test confirming it satisfies `where TResponse : IUnion`, that its `Value` is always `null`, and that it carries no case-construction support (attempting `IOutcomeCaseRegistry.Construct<Outcome, Cancelled>` fails clearly rather than silently).
- Arity 1 (`Outcome<T>`): full parity tests with the existing arity-2-through-16 test suites for `Match`/`Switch`/`TryGetValue`/`ToString`/equality, adapted for the single-case shape (`TryGetValue` always succeeds; `Match`/`Switch` take exactly one delegate).
- Every existing test exercising the old non-generic `Outcome` (`Success | Failure`) is either updated to the new arity-0 semantics or migrated to an explicit `Outcome<Success, Failure>` (arity 2), matching whichever this PRD's own doc/example migration lands on for that call site.
- Prior art: `tests/Interlocutor.CommonKernel.Tests` already has full arity-2-through-6 coverage (`Match`/`Switch`/`TryGetValue`/equality/`ToString`) - mirror its structure for the new arity-1 tests; `tests/Interlocutor.Generator.Tests`'s existing `INTERLOC011` tests confirm the floor stays enforced for consumer-declared unions.

## Out of Scope

- The `T1..TN` case-type-parameter rename for arity 2 through 16 - tracked separately as `.scratch/outcome-naming-and-arity-refactor/issues/08` (already `ready-for-agent`).
- `IVoidCommandHandler` → `IBareCommandHandler` (and its wrapper types) - tracked separately as `.scratch/bare-command-rename/`.
- Raising the arity ceiling or adding a large-arity warning - tracked separately as `.scratch/outcome-naming-and-arity-refactor/issues/09` and `10`, unaffected by this work.
- Any change to `OutcomeMapperBase<TResult>`/`IOutcomeMapper<TResult>` - tracked separately as `.scratch/outcome-mapper-custom-case-registry/`.
- Removing or deprecating `IOutcome`/`IOutcomeCase` themselves - explicitly not part of this design; only their role as the response constraint changes.

## Further Notes

- This directly extends ADR-0022's already-decided principle ("no case type carries a universal, context-independent success/failure meaning") to the type-shape level: the old arity-0 `Outcome` baked in a privileged Success/Failure judgment structurally, which is the same assumption ADR-0022 rejected at the value-classification level.
- This is a breaking change with no compatibility shim, consistent with this project's pre-1.0, no-stable-release stance already exercised for ADR-0018, ADR-0021, and ADR-0022's own breaking removals.
- A retrospective ADR recording this decision (in the style of ADR-0022, written after the shipped change rather than before) is expected once this work lands, per this project's established pattern - not written as part of this PRD.
