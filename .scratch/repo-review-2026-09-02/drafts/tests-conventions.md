## [CRITICAL] FluentValidationErrors never got the order-independent, content-based equality ticket 01/commit d5c9a80 promised
- File: src/Interlocutor.FluentValidation/FluentValidationErrors.cs:30-116
- Category: test-coverage
- Summary: `FluentValidationErrors` relies on compiler-synthesized record-struct equality over a plain `IReadOnlyList<ValidationFailure>?` field, so two instances built from equal-content-but-different-instance lists are unequal - verified empirically, and nothing in the test suite catches it.
- Detail: `.scratch/outcome-value-equality/issues/01-order-independent-aggregate-equality.md` explicitly lists `FluentValidationErrors` as one of six aggregate types that must "compare equal when they hold the same distinct items regardless of the order those items were collected in," with the fix meant to live once in `DistinctItemSet<TItem>`, which the other five types (`Failures`, `Failures<TErrorCode>`, `Conflicts`, `ValidationErrors`, `ValidationErrors<TErrorCode>`) compose. `FluentValidationErrors`, however, deliberately does **not** compose `DistinctItemSet<TItem>` - its own code comment says so ("Not `DistinctItemSet<TItem>`-typed like the other five aggregate types' backing fields... this type preserves every failure verbatim rather than deduplicating"). It has no `Equals`/`GetHashCode` override of its own, so it falls back to the record struct's compiler-synthesized field equality, which compares `_failures` via `EqualityComparer<IReadOnlyList<ValidationFailure>?>.Default` - reference equality for a `List<T>`/array, not content equality. I verified this by temporarily adding `Assert.Equal(new FluentValidationErrors([failure]), new FluentValidationErrors([failure]))` (same `ValidationFailure` instance, two different backing arrays) to `FluentValidationErrorsTests.cs` and running it: it fails with "Values differ" even though `ToString()` prints identically for both sides. Concretely: a handler that builds this failure case twice from equivalent validator output (e.g. a retried validation pass, or two requests that fail the same way) gets a case value that silently fails to `==`/`Assert.Equal` against an otherwise-identical instance - this is exactly the kind of regression `outcome-value-equality`'s own acceptance criteria were written to catch, and no test in `tests/Interlocutor.FluentValidation.Tests/FluentValidationErrorsTests.cs` exercises `Equals`/`GetHashCode`/`==` at all.
- Suggested action: Either give `FluentValidationErrors` its own content-based `Equals`/`GetHashCode` (comparing `Failures` order-independently, consistent with the other five types), or compose `DistinctItemSet<ValidationFailure>` the way the others do if verbatim (non-deduplicated) ordering can be preserved through it; then add the same order-independent-equality + hash-code-agreement + inverse (differing items unequal) + default-vs-explicit tests ticket 01 required for the other five types.

## [HIGH] No direct equality/hashcode tests on the aggregate result types themselves - only indirect coverage through Outcome
- File: tests/Interlocutor.CommonKernel.Tests/AggregateResultTypesTests.cs
- Category: test-coverage
- Summary: `Conflicts`, `ValidationErrors`, `ValidationErrors<TErrorCode>`, and `Failures<TErrorCode>` have no test anywhere that calls `Equals`/`GetHashCode`/`==` on them directly; the one order-independent-equality test that exists covers only `Failures` (non-generic), and only indirectly, wrapped inside an `Outcome<string, Failures>`.
- Detail: `.scratch/outcome-value-equality/issues/01-order-independent-aggregate-equality.md`'s acceptance criteria explicitly require: "Test coverage proves this (order-independent equality + hash-code agreement) for at least `Failures` and one of the generic (`<TErrorCode>`) variants," "Test coverage proves the inverse: instances with extra items, missing items, or differing items are unequal," and "Default (zero-initialized) instances remain equal to each other and unequal to any explicitly-constructed instance." None of these are met: `tests/Interlocutor.CommonKernel.Tests/AggregateResultTypesTests.cs` (the file covering `Failures`/`Conflicts`/`ValidationErrors`) has zero `Assert.Equal`/`GetHashCode` calls on the aggregate types themselves - only on their `Items`/`ToString()` output. The sole order-independent-equality proof in the whole solution is `OutcomeEqualityTests.Outcome_PairedWithFailures_IsEqualRegardlessOfTheOrderItsItemsWereCollectedIn`, which tests `Failures` only, and only through `Outcome<string, Failures>.Equals` delegating to `Value.Equals` - it never calls `Failures.Equals` directly, never covers a `<TErrorCode>` generic variant, never tests the "differing items are unequal" inverse for any of these types, and never tests default-vs-explicit-instance equality for them. A regression that broke `Conflicts.Equals`, `ValidationErrors<TErrorCode>.GetHashCode`, or the "same default, different explicit" invariant on any of these four types would ship with the full test suite green.
- Suggested action: Add direct `Equals`/`GetHashCode`/`==` tests to `AggregateResultTypesTests.cs` (or a new equality-focused file alongside it) for `Conflicts`, `ValidationErrors`, `ValidationErrors<TErrorCode>`, and `Failures<TErrorCode>`, covering: order-independent equality with agreeing hash codes, inequality on extra/missing/differing items, and default-vs-default (equal) vs. default-vs-explicit (unequal) - the same shape of coverage `OutcomeEqualityTests` already gives the `Outcome` union, applied to the aggregate types on their own terms rather than only through a wrapping `Outcome`.
