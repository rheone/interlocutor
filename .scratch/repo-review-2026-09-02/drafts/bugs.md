# Bugs / Correctness Review — 2026-09-02

Lane: BUGS / CORRECTNESS. Scope: `src/*` and `TutorialProject/`.

## [CRITICAL] A null reference-type (or null `Nullable<T>`) case value is indistinguishable from "no case set" across every `Outcome` arity
- File: src/Interlocutor.CommonKernel/Outcome.cs:24 (also applies to every arity declared in this file, lines 24-143)
- Category: bug
- Summary: Every `Outcome`/`Outcome<...>` union stores its active case as a single boxed `object Value` field with no separate discriminator, so a legitimately successful (or failed) outcome whose case payload is `null` — a `null` reference-type value, or a `Nullable<T>` with `HasValue == false` — becomes bit-for-bit identical to an unset/default union. `IsSuccess` reports `false`, `TryGetValue` fails for every case, `Match`/`Switch` throw `InvalidOperationException("Outcome holds no recognized case value.")`, and `Interlocutor.AspNetCore.ResultExtensions`'s hand-written switches throw `NotImplementedException` — all for an outcome a handler legitimately constructed as a success.
- Detail: Verified empirically by constructing `Outcome<string?, NotFound> result = (string?)null;` (a wholly legal, common shape — e.g. a handler that succeeds but has nothing to return, or an update that legitimately produces a null field) and reflecting/exercising the generated members against the actual built library:
  - `result.IsSuccess` → `false` (should be `true`; the operation succeeded)
  - `result.TryGetValue(out string? s)` → `false`, and `result.TryGetValue(out NotFound nf)` → `false` — *neither* case reports true
  - `result.Match(s => ..., nf => ...)` → throws `System.InvalidOperationException: Outcome holds no recognized case value.`
  - Reflecting the type shows exactly one backing field, `Object <Value>k__BackingField`, confirming there is no separate tag/discriminator the compiler-generated `union` (nor `Interlocutor.Generator`'s emitted members) could consult to recover "this was the Success case, holding null" — the information is lost the instant the case value is boxed into `Value`.
  - Root cause is structural: `src/Interlocutor.Generator/OutcomeMemberEmitter.cs`'s `EmitIsSuccess` (`this.Value is <firstCaseType>`), `EmitMatch`/`EmitSwitch` (`switch (this.Value) { <caseType> caseN => ... }`), and `EmitTryGetValueOverloads` (`this.Value is <caseType> matched`) all rely on a C# type-pattern match against `this.Value`, and a type pattern **never matches `null`** per the C# language spec — so every one of these generated members silently mis-handles a null-payload case the exact same way, for every arity 2 through 6.
  - This is not merely cosmetic: `src/Interlocutor.Abstractions/Pipeline/Classifiers/OutcomeClassifierBuilder.cs`'s `DefaultOutcomeClassifier.IsFailure` unwraps the union via `IUnion.Value`, and when that unwrapped value is `null` none of the type-keyed classifications or predicates match, so the classifier's documented fail-closed policy kicks in and reports `IsFailure(result) == true`. Both `src/Interlocutor.Persistence.EntityFrameworkCore/UnitOfWorkBehavior.cs` and `src/Interlocutor.Persistence.NHibernate/UnitOfWorkBehavior.cs` gate transaction commit/rollback on exactly this classifier. Concretely: a handler that legitimately succeeds and returns `Outcome<SomeDto?, NotFound>`/`Outcome<string?, Conflict>`/etc. with a `null` success payload will have its transaction **rolled back instead of committed**, even though nothing failed — the write is silently lost.
  - Also reachable from `src/Interlocutor.Abstractions/Pipeline/AuditingBehavior.cs` and `LoggingBehavior.cs` (both call the same describer/classifier), so such a request is also logged/audited as a failure it never was.
- Suggested action: Give the `union`-backed `Outcome` types a way to distinguish "case N set, value null" from "no case set" — for example, box `null` case payloads into a private sentinel wrapper before storing, or (if the underlying preview `union` language feature exposes one) use a real discriminator/tag rather than pattern-matching `Value` alone — and update `OutcomeMemberEmitter`'s generated `IsSuccess`/`TryGetValue`/`Match`/`Switch` to consult it. At minimum, until fixed, document the hazard prominently (README/CLAUDE.md/glossary) so consumers know never to use a nullable reference type or `Nullable<T>` as an `Outcome` case's payload type, and add regression tests for a null-payload case to `Interlocutor.CommonKernel.Tests` and the `UnitOfWorkBehavior` transaction tests for both stores.
