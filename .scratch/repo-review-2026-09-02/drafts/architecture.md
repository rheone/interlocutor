## [HIGH] `Interlocutor.Generator`'s documented wiring on Abstractions does not exist in the project graph
- File: src/Interlocutor.Abstractions/Interlocutor.Abstractions.csproj (no reference present); actual reference lives at src/Interlocutor.CommonKernel/Interlocutor.CommonKernel.csproj:23-27
- Category: architecture
- Summary: CLAUDE.md, README.md, and documentation/glossary.md all state `Interlocutor.Generator` "rides in as a `PrivateAssets=\"all\"` analyzer reference on `Interlocutor.Abstractions`," but `Interlocutor.Abstractions.csproj` carries no reference to the generator at all — the only `ProjectReference` to `Interlocutor.Generator` anywhere in `src/` is on `Interlocutor.CommonKernel`, for an unrelated purpose.
- Detail: `Interlocutor.Abstractions.csproj` (read in full) contains exactly one `ItemGroup` with a `ProjectReference` to `Interlocutor.CommonKernel` and nothing else generator-related. The sole `src/` reference to `Interlocutor.Generator.csproj` is in `Interlocutor.CommonKernel.csproj`, and its own inline comment explains it is there only so `OutcomeMemberGenerator` can generate `Outcome`/`Outcome<...>`'s `Match`/`Switch`/etc. members for CommonKernel's *own* compilation — nothing to do with the handler-discovery generator behavior CLAUDE.md/README are describing. `Interlocutor.Generator.csproj` itself confirms the real model in its own comment: "a consumer referencing `Interlocutor.Generator` gets it wired up as an analyzer/generator automatically" — i.e. a consumer must add that reference themselves; it is not transitively pulled in by referencing `Interlocutor.Abstractions`. This is corroborated by `TutorialProject/TodoTasks.Api` (grepped for `Interlocutor.Generator` — zero matches) using `ScanAssembly` (runtime reflection) instead, exactly as `documentation/beginners-guide-todo-api.md:1764` describes: "There's a separate, additive compile-time path via `Interlocutor.Generator`/`AddGeneratedRegistrations` that this guide doesn't use." So the shipped sample app itself demonstrates that referencing `Interlocutor.Abstractions` alone does **not** get you compile-time handler discovery — directly contradicting the "rides in on Abstractions" claim in the very file (CLAUDE.md) this review is instructed to treat as load-bearing. `DependencyTests.cs` has no assertion at all involving the Generator assembly, so nothing in the test suite would catch this claim being wrong or drifting further.
- Suggested action: Either (a) correct CLAUDE.md/README.md/glossary.md to describe `Interlocutor.Generator` as an opt-in package a consumer references directly (matching `Interlocutor.Generator.csproj`'s own comment and the TutorialProject's actual usage), or (b) if the intent was always for `Interlocutor.Abstractions` to carry the analyzer automatically, add that `PrivateAssets="all"` analyzer reference to `Interlocutor.Abstractions.csproj` so the shipped package matches the documented architecture. Either way, add a `DependencyTests.cs` assertion pinning whichever behavior is chosen so this can't silently drift again.

## [HIGH] `ResourceCommandHandler.Authorize` routes access-denial through generic `Failure` instead of the purpose-built `Forbidden` case
- File: src/Interlocutor.Abstractions/Commands/ResourceCommandHandler.cs:25-26, 42, 76-79
- Category: architecture
- Summary: The library's own built-in resource-authorization template hard-codes its outcome shape to `Outcome<TSuccess, NotFound, Failure>`, so a denied `Authorize` call can only ever surface as `Failure` — never `Forbidden` — even though `Forbidden` exists in `CommonKernel` specifically to represent "access denied."
- Detail: CLAUDE.md's result-type convention says "don't route every handler failure through a single generic `Failure`. Pick the specific `Outcome<TSuccess, ...>` arity/case types that operation can actually produce." `AuthorizationBehavior<TRequest,TResponse>` (src/Interlocutor.Abstractions/Pipeline/AuthorizationBehavior.cs:76) correctly follows this: a denied policy check constructs a `Forbidden`. But `ResourceCommandHandler<TCommand,TEntity,TSuccess>` — the library's *other* built-in authorization mechanism, documented side-by-side with `AuthorizationBehavior` in documentation/handler-selection-and-dispatch.md's "Contrast: Resource vs. Non-Resource Authorization" section as solving the same class of problem ("Can this user do X to *this* resource?") — is generic over `TCommand : ICommand<Outcome<TSuccess, NotFound, Failure>>` and its `Authorize` abstract method returns `Failure?`. A denied resource-authorization check is therefore structurally indistinguishable from any other unclassified failure a handler might produce; a caller (e.g. `Interlocutor.AspNetCore`'s `ToActionResult()`) cannot map "not authorized to touch this entity" to a distinct outcome the way it can for the non-resource `Forbidden` case, and there is no way for a consumer to fix this by picking a different outcome shape — the base class's `Handle` method's signature fixes it. Every example in the shipped docs (including the `DeleteDocumentHandler` walkthrough) inherits this shape.
- Suggested action: Widen `ResourceCommandHandler`'s fixed shape to `Outcome<TSuccess, NotFound, Forbidden>` (or `Outcome<TSuccess, NotFound, Forbidden, Failure>` if a truly-unclassified failure case is still needed for other operational errors surfaced during `HandleAsync`), and change `Authorize` to return `Forbidden?`. This is a breaking API change, so it should go through the same deprecation/versioning path other Outcome-arity changes in this repo have used (see `.scratch/outcome-naming-and-arity-refactor/`).

## [MEDIUM] `IUnitOfWork.Cancel()` disposes the rolled-back transaction in EF Core but not in NHibernate
- File: src/Interlocutor.Persistence.EntityFrameworkCore/EntityFrameworkUnitOfWork.cs:55-65 vs. src/Interlocutor.Persistence.NHibernate/NHibernateUnitOfWork.cs:54-63
- Category: architecture
- Summary: The two `IUnitOfWork` implementations handle the same documented "rare-case escape hatch" (`Cancel()`) inconsistently: EF Core rolls back *and* disposes the transaction object it retrieved; NHibernate only rolls back.
- Detail: `EntityFrameworkUnitOfWork.Cancel()` does `await transaction.RollbackAsync(...)` then `await transaction.DisposeAsync()` before clearing the tracker. `NHibernateUnitOfWork.Cancel()` does `await transaction.RollbackAsync(...)` only, then `s.Clear()` — the `ITransaction` object obtained from `GetCurrentTransaction()` is never disposed. Per `UnitOfWorkBehavior`'s own doc comments on both sides ("...or an explicit `IUnitOfWork.Cancel` already cleaned up..."), the store-specific `UnitOfWorkBehavior` deliberately treats a cancelled dispatch as fully finalized and never touches the transaction again — so nothing else in the pipeline disposes the NHibernate transaction reference `Cancel()` rolled back, whereas EF Core's counterpart is disposed exactly once, deterministically, at the point of cancellation. `IUnitOfWork`'s own XML doc claims the "unit-of-work-owned transaction model" applies uniformly regardless of store, which this asymmetry doesn't quite honor — even if NHibernate's `ISession.Dispose()` may eventually clean up an undisposed child transaction when the scope ends, that's an implicit, store-internal safety net rather than the explicit, symmetric behavior the EF Core side documents and performs.
- Suggested action: Either dispose the NHibernate transaction explicitly in `Cancel()` (mirroring the EF Core side, with the same `IDISP004` suppression/justification comment pattern used elsewhere in these two files), or, if leaving it undisposed is intentional (e.g. because NHibernate's `ITransaction` disposal is known to be a no-op after `RollbackAsync`), add a comment explaining the asymmetry so a future reader doesn't "fix" it into an inconsistency with EF Core, or vice versa.

## [MEDIUM] `IExternalStoreRequest`'s XML doc describes the classic local-transactional-outbox pattern, but the marker does the opposite of what that pattern needs
- File: src/Interlocutor.Abstractions/Markers/IExternalStoreRequest.cs:3-20
- Category: architecture
- Summary: The marker's doc comment invites use for "outbox, event bus, saga storage" durability, but the mechanism it actually drives (`UnitOfWorkBehavior` in both persistence packages) *excludes* the request from local transaction management entirely — the opposite of what the well-known transactional-outbox pattern needs (the outbox row and the domain write must share one local transaction to be atomic).
- Detail: The marker's first remarks paragraph reads: "Implement this marker interface on commands when the handler's response should be durably persisted to an external system (outbox, event bus, saga storage) after successful execution. This pattern ensures reliable event delivery even if the message broker or external system is temporarily unavailable." That is exactly the motivation for the transactional outbox pattern, whose defining property is that the outbox write and the domain write are wrapped in the *same* local database transaction so neither can commit without the other. But the second paragraph, and both `UnitOfWorkBehavior` implementations' own comments (`EntityFrameworkCore/UnitOfWorkBehavior.cs:79-91`, `NHibernate/UnitOfWorkBehavior.cs:86-89`), say the marker does the reverse: it suppresses local transaction management for the entire request, "even if the handler touches the scoped context/session." A consumer who reaches for this marker because they read "outbox" in its doc and want atomicity between a domain write and an outbox-table insert would get no local transaction wrapping either write at all — silently defeating the atomicity the pattern exists to provide, with no compiler or runtime signal that anything is wrong. (A locally-written outbox table is arguably not what this marker is *for* — it may be intended only for requests whose durability comes entirely from an external system's own guarantees — but the doc comment as written doesn't make that distinction, and "outbox" is conventionally understood as the local-table pattern.)
- Suggested action: Rewrite the first remarks paragraph to explicitly rule out the local-transactional-outbox use case (or, if that use case genuinely doesn't need this marker, delete the "outbox" example from the list entirely and keep only "event bus, saga storage" or similar external-durability examples where the request truly has no local write to protect). Cross-reference `ITransactionalRequest` and `UnitOfWorkBehavior`'s own remarks so the two markers' relationship reads unambiguously from either side.
