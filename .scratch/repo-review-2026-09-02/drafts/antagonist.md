# Part 1: Verdicts on existing findings

## bugs.md

### [CONFIRMED] A null reference-type (or null `Nullable<T>`) case value is indistinguishable from "no case set" across every `Outcome` arity
Verified empirically against the real compiled library, not just by reading source. Built and ran a throwaway xunit test (`tests/Interlocutor.CommonKernel.Tests/ZZZThrowawayNullCaseProbeTests.cs`, deleted afterward - repo left clean, `git status --short` empty) on the actual `net11.0` preview SDK installed in this environment (`11.0.100-preview.6.26359.118`), which really does ship the `union`/`IUnion` language feature this repo depends on (`System.Runtime.CompilerServices.IUnion`, confirmed real via the shipped SDK, not a repo-invented type):

```
Outcome<string?, NotFound> result = (string?)null;
result.IsSuccess               -> False
result.TryGetValue(out string?)-> False
result.TryGetValue(out NotFound) -> False
result.Match(...)              -> InvalidOperationException: "Outcome holds no recognized case value."
reflected instance fields      -> exactly one: Object <Value>k__BackingField
```

This settles it: there is no hidden discriminator, and the generated members genuinely mis-handle a null-payload case for every arity, exactly as claimed. I also read `OutcomeMemberEmitter.cs` in full and confirmed `EmitIsSuccess`/`EmitTryGetValueOverloads`/`EmitMatch`/`EmitSwitch` are all built on `this.Value is <caseType>` or `switch (this.Value) { <caseType> ... }` - C# type patterns, which never match `null` regardless of the declared case type's nullability. This is a real, structural gap, not a doc/spec misunderstanding.

I additionally traced the consequence chain myself: `OutcomeClassifierBuilder.DefaultOutcomeClassifier.IsFailure` (`src/Interlocutor.Abstractions/Pipeline/Classifiers/OutcomeClassifierBuilder.cs:167-190`) unwraps via `IUnion.Value`; for a null-payload case, `Unwrap` returns `null`, no type registration or predicate matches `null`, and the fail-closed policy (`return true;` at line 189) reports the outcome as a failure. Both `src/Interlocutor.Persistence.EntityFrameworkCore/UnitOfWorkBehavior.cs` (read in full) and `src/Interlocutor.Persistence.NHibernate/UnitOfWorkBehavior.cs` gate `if (!this.classifier.IsFailure(result)) { ...commit... } else { ...rollback... }` on exactly this classifier - so a handler that legitimately succeeds with a null success payload really does get its transaction rolled back. `AuditingBehavior` (`src/Interlocutor.Abstractions/Pipeline/AuditingBehavior.cs:28-29,45`) independently confirmed to construct its own `DefaultResponseOutcomeDescriber(OutcomeClassifierBuilder.DefaultClassifier)`, so the mislabeling reaches audit logs too, as claimed.

Severity: CRITICAL is correct, not inflated. This is a silent, no-exception-visible-to-the-caller data-loss bug (a successful write is rolled back) reachable through an entirely ordinary, legal C# construction (`Outcome<string?, NotFound>` returning `null`) that nothing in the type system or the library's own docs warns against. The "Detail" writeup in the draft is accurate down to the exact exception message and field name; nothing to correct.

One thing worth adding for whoever picks this up (see Part 2): the same root cause has a *third*, distinct failure mode in `Interlocutor.AspNetCore`'s reflective mapping path (`DefaultOutcomeCaseRegistry.TryGetActiveCase` + `ResultExtensions.ExtractCase`) that this finding's "Detail" section doesn't mention - it doesn't throw or return false, it returns `true` with a bogus `caseType`. Logged separately in Part 2 so it isn't lost, but it's the same underlying bug and should be fixed by the same change.

### [CONFIRMED] `IUnitOfWork.Cancel()` disposes the rolled-back transaction in EF Core but not in NHibernate
Read both `Cancel()` implementations in full. Confirmed exactly: `EntityFrameworkUnitOfWork.Cancel()` does `RollbackAsync` then `DisposeAsync`; `NHibernateUnitOfWork.Cancel()` does `RollbackAsync` only, never disposing the `ITransaction` obtained from `GetCurrentTransaction()`. Real asymmetry. I'd note the practical severity is probably closer to LOW-MEDIUM rather than a clear MEDIUM: NHibernate's `ITransaction` typically wraps the ADO.NET `DbTransaction`, and the owning `ISession`'s own disposal (at end of DI scope) will eventually release it - it's not a definite leak the way an undisposed `DbConnection` would be, just an inconsistency with the EF Core side's explicit, deterministic disposal. Keeping the finding at MEDIUM as filed is defensible given the codebase's demonstrated attention to `IDisposableAnalyzers`-clean code elsewhere, but flagging that the real-world blast radius is smaller than "resource leak" framing might suggest.

# Part 2: New findings from independent gap-hunt

## [HIGH] The same null-payload/no-discriminator bug silently corrupts `Interlocutor.AspNetCore`'s reflective outcome-to-HTTP mapping path, via a code path bugs.md's lane didn't examine
- File: src/Interlocutor.Abstractions/Pipeline/Cases/DefaultOutcomeCaseRegistry.cs:55-72 (`TryGetActiveCase`); src/Interlocutor.AspNetCore/ResultExtensions.cs:415-436 (`ExtractCase`)
- Category: bug (same root cause as bugs.md's CRITICAL finding; distinct symptom/blast radius, in a package that lane's "Detail" section doesn't mention at all)
- Summary: For a successful outcome with a null case payload, `IOutcomeCaseRegistry.TryGetActiveCase` returns `true` (not `false`, and doesn't throw) but reports the *outcome's own container type* as the active case type - a value that is never a real, registered case - so `Interlocutor.AspNetCore`'s generic `ToActionResult()` catch-all silently gets fed garbage instead of failing loudly or succeeding correctly.
- Detail: `DefaultOutcomeCaseRegistry.TryGetActiveCase` (read in full): `if (response is IUnion union) { caseValue = union.Value; caseType = caseValue?.GetType() ?? typeof(TResponse); return true; }`. For a null-payload success case, `union.Value` is `null`, so `caseValue = null` and - because `null?.GetType()` is `null` - `caseType` falls back to `typeof(TResponse)`, the *entire outcome union type itself*, not any real case type, while still returning `true` ("found it"). `ResultExtensions.ExtractCase<TResponse>` (read in full) calls this and then classifies via `OutcomeClassifierBuilder.DefaultClassifier.IsFailure(caseValue)` with `caseValue = null` - the same fail-closed path bugs.md traced for `UnitOfWorkBehavior` - so a legitimately successful null result is reported as `IsFailure = true` with `CaseType = typeof(TResponse)`. Whatever calls `ExtractCase` for the reflective catch-all overload (the one used, per `ResultExtensions.cs`'s own doc comments at lines 301, 324, 353, for "any compiler-generated union" not covered by a dedicated arity overload) then attempts `InvokeMap(mapper, typeof(TResponse), null)`, which `MakeGenericMethod`s `Map<TResponse>` on the status mapper - a type argument no `IOutcomeStatusMapper` implementation will have a real overload or registration for, since it's the outcome type, not a failure case type. Depending on the mapper implementation, this either throws an unhelpful reflection-shaped exception at the boundary of an ASP.NET Core action, or (if a generic fallback overload happens to bind) maps a legitimately successful null result to a failure HTTP status.
- Suggested action: Fix at the root - the same discriminator fix bugs.md's finding calls for (giving null-payload cases a way to be recognized as "case N, value null" rather than "no case") - should make `TryGetActiveCase` correctly report the real case type (e.g. `string` for `Outcome<string?, NotFound>`'s success case) even when the boxed value is null. Once that's fixed, add a regression test exercising `ToActionResult()` (or the equivalent `IOutcomeStatusMapper` catch-all path) for a null-payload success outcome specifically, since this is a different code path than the one `Interlocutor.CommonKernel.Tests`/`UnitOfWorkBehavior` tests would cover.

## [MEDIUM] `global.json`'s `rollForward: latestMajor` on a preview-only SDK whose build depends on a preview-only language feature is a build-stability risk this repo can't currently detect
- File: global.json:2-5
- Category: architecture / CI (build configuration)
- Summary: The solution pins `"version": "11.0.100-preview.6.26359.118"` but sets `"rollForward": "latestMajor"`, meaning any machine (a future CI runner, a contributor's later `dotnet` install) with a *newer major* SDK installed will silently build with that SDK instead - a real risk specifically because this repo's core type (`Outcome`) depends on the still-preview `union` declaration syntax, whose availability and exact codegen are exactly the kind of thing that could change or be removed across a major SDK bump while still preview.
- Detail: Verified this environment already has two SDK majors installed side by side (`10.0.400` and `11.0.100-preview.6.26359.118`, via `dotnet --list-sdks`) - proof that "more than one major SDK present on the machine" is not a hypothetical for this project's environment, only that today's higher major (`11`) happens to be the pinned one so nothing has silently rolled forward yet. If a `12.x` SDK is ever installed on a build agent before this repo's `global.json` is deliberately bumped, `rollForward: latestMajor` will pick it up automatically and build with a compiler this repo has never validated against the `union`/`partial union` declarations `Interlocutor.CommonKernel` and `Interlocutor.Generator` depend on (`Interlocutor.Generator.csproj`'s own comment already flags that even the *current* `Microsoft.CodeAnalysis.CSharp` package's `UnionDeclarationSyntax` is marked `[Experimental]`/`RSEXPERIMENTAL006` - i.e., the language team itself considers this surface unstable). This interacts with tests-conventions.md's csharpier finding: both are examples of the preview-syntax dependency creating tooling/build fragility the repo hasn't fully hardened against.
- Suggested action: Consider `"rollForward": "latestFeature"` or `"latestPatch"` instead, so the pinned major/minor (and therefore the preview language surface) can't silently change out from under the build; if `latestMajor` is deliberate (e.g., to make on-ramping to GA .NET 11 easy later), leave a comment in `global.json` explaining the choice given the preview-feature dependency, since the tradeoff isn't obvious from the file alone.

## [MEDIUM] `ResourceCommandHandler`'s fixed `Outcome<TSuccess, NotFound, Failure>` shape means a nullable `TSuccess` hits the exact same null-discriminator bug bugs.md found, and CLAUDE.md's convention advice makes this more likely, not less
- File: src/Interlocutor.Abstractions/Commands/ResourceCommandHandler.cs:26 (generic constraint), interacting with src/Interlocutor.CommonKernel/Outcome.cs (the null-payload bug)
- Category: architecture + bug (cross-lane interaction between architecture.md's finding #2 and bugs.md's CRITICAL finding, which the single-lane reviews couldn't surface since neither lane read the other's target file)
- Summary: Because `ResourceCommandHandler<TCommand, TEntity, TSuccess>` lets a consumer choose any `TSuccess`, a consumer who picks a nullable `TSuccess` (e.g. `string?`, or any reference type where "succeeded, nothing to return" is meaningful) and returns `null` from `HandleAsync` hits bugs.md's CRITICAL null-discriminator bug through this library's own built-in template method - not just through hand-written handler code - and `UnitOfWorkBehavior` will roll back that dispatch's transaction even though `ResourceCommandHandler.Handle` itself completed normally with what the consumer intended as a genuine success.
- Detail: This isn't independently new - it is bugs.md's CRITICAL finding, but concretely reachable through a code path none of the four lanes' findings connect: architecture.md's finding #2 flags `ResourceCommandHandler`'s fixed outcome shape as a design smell (`Forbidden` vs `Failure`) without noting the shape's `TSuccess` slot is also exposed to the null-discriminator hazard, and bugs.md's finding never mentions `ResourceCommandHandler` at all. A consumer who reads CLAUDE.md's result-type convention ("don't route every handler failure through a single generic `Failure`... pick the specific arity/case types") and then reasonably wants a resource-mutation handler (e.g. a "mark as read"/"archive" style command) to return `Outcome<string?, NotFound, Failure>` where the success case is an optional generated id, is walking directly into the CRITICAL bug via the library's own recommended template-method entry point.
- Suggested action: No separate fix needed beyond bugs.md's root-cause fix (the discriminator itself) - but when writing the regression tests bugs.md's finding calls for, include one routed through `ResourceCommandHandler`/`UnitOfWorkBehavior` together, not only through bare `Outcome<...>` construction, since that's the realistic path a consumer following the library's own documented patterns would hit this through.
