# 01 - Spike: does Eject.WithCase reach a non-behavior template-method consumer?

**What to build:** Prototype `ResourceCommandHandler<TCommand, TEntity, TResponse>` generic over `TResponse : IUnion` instead of the current fixed `Outcome<TSuccess, NotFound, Forbidden>` shape, ejecting `NotFound` and `Forbidden` via the already-shipped `Eject.WithCase<TCase>` (see `AuthorizationBehavior.cs`'s remarks and `PipelineEjectCaseException` for the mechanism as it exists today) instead of constructing them directly.

The open question this spike exists to answer: `Eject.WithCase` today is caught by the mediator's own pipeline-dispatch wrapper (`QueryHandlerWrapper`/`CommandHandlerWrapper`/the generator's emitted equivalents), which is the one place that knows `TResponse` concretely for an `IPipelineBehavior<TRequest, TResponse>` in the chain. `ResourceCommandHandler` is not a pipeline behavior - it's a template-method base class a concrete handler inherits from and separately declares as `ICommandHandler<TCommand, TResponse>` (see `documentation/sample-app-walkthrough.md`'s note on why that explicit interface declaration is required for handler discovery). Determine whether an ejected exception thrown from inside `ResourceCommandHandler.HandleAsync` actually reaches that same wrapper-side catch site given that indirection, or whether it needs its own catch point (and if so, where one could live without reintroducing a per-consumer `IOutcomeCaseRegistry` dependency, which is exactly what `Eject.WithCase` was built to avoid).

This is a spike to size the blast radius and prove (or disprove) feasibility, not a design already accepted - mirrors `pipeline-case-fidelity/07`'s own framing for the same mechanism's original introduction.

## Comments

Implemented in commit `be5adbb` ("feat: ResourceCommandHandler ejects NotFound/Forbidden via Eject.WithCase"), already present on this branch before this pass started. This pass re-verified the work rather than redoing it (`dotnet build`, `dotnet test` on `Interlocutor.Abstractions.Tests` and the `TodoTasks.Api.Tests` unit-level `UpdateTodoTaskHandlerTests`, and a full solution `dotnet test`) and found nothing left to change.

**Blast-radius write-up:**

- `ResourceCommandHandler<TCommand, TEntity, TResponse>` is now generic over `TResponse : IUnion` instead of the fixed `Outcome<TSuccess, NotFound, Forbidden>` shape, and ejects `NotFound`/`Forbidden` via `Eject.WithCase<TCase>` from both short-circuit points in `HandleAsync` (missing entity, denied `Authorize`) instead of constructing them directly.
- **The open question is answered: the existing wrapper-side catch already covers this path, with no new catch point needed.** `ResourceCommandHandler` is a template-method base class, not a pipeline behavior, but a concrete subclass is still registered and dispatched as an ordinary `ICommandHandler<TCommand, TResponse>`. The mediator's `CommandHandlerWrapper` resolves that handler and hands its `HandleAsync` method - which, for a subclass, resolves to this base class's public `HandleAsync(TCommand, CancellationToken)` - to `PipelineChainExecutor.ExecuteAsync` as the innermost delegate. That executor already wraps the innermost delegate call in a `try`/`catch` for `PipelineEjectCaseException` before any `IPipelineBehavior<,>` runs, so the eject unwinds no further than that same catch regardless of the template-method indirection.
- Proved empirically, not just by code reading: `ResourceCommandHandlerEjectCaseEndToEndTests` dispatches through a real `Mediator` with **zero pipeline behaviors registered** (deliberately, unlike `AuthorizationBehaviorEjectCaseEndToEndTests`, which needs `AuthorizationBehavior` in the chain to have something to eject from). With no behavior in the chain, the wrapper/executor path is the *only* thing that could possibly catch the eject - and the tests observe ordinary constructed `NotFound`/`Forbidden`/success responses back at the `SendAsync` caller, not a leaked `PipelineEjectCaseException`.
- `UpdateTodoTaskHandler` (`TutorialProject/TodoTasks.Api/Features/Tasks/UpdateTodoTask/UpdateTodoTaskHandler.cs`) is the migrated worked example - its `Outcome<TodoTaskDto, NotFound, Forbidden>` response shape is unchanged, only the base class's internals changed to eject instead of construct.
- Surprise/consequence worth flagging for issue 02: because `TResponse` is no longer known to `ResourceCommandHandler` itself, a subclass's short-circuit paths (not-found/forbidden) can no longer be observed as a plain return value from a direct `HandleAsync` call that bypasses the mediator - such a call now throws `PipelineEjectCaseException` instead of returning a constructed case. Tests that previously asserted short-circuit behavior by calling the handler directly had to be rewritten to either dispatch through a real `ISender`/`Mediator` (so the wrapper/executor catch applies) or assert the thrown exception directly. This is a real behavioral change for any direct/unit-style caller of a `ResourceCommandHandler` subclass, not just an internal implementation detail - issue 02 should weigh it when deciding whether to accept the mechanism.
- No change to the dispatch/wrapper machinery itself was needed to make this reach; `PipelineChainExecutor`'s existing catch, originally built for `AuthorizationBehavior`, is generic over the innermost delegate's `TResponse` and doesn't care whether that delegate belongs to a behavior or a template-method base class's `HandleAsync`.
