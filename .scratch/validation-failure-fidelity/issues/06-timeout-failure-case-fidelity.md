# 06 - `Timeout` failure-case fidelity

Status: split - generic mapper recognition done; concrete second implementation remains needs-triage

## Labels

done, needs-triage

A specific `ITimeoutPolicy` implementation - e.g. a Polly-backed policy - might want to expose its own policy context/tags beyond the generic `Timeout` struct's `Budget`/`Elapsed`/`Message`. The same treatment given to validation in this feature (issues 01-04) would apply cleanly here: a technology-specific case type and companion behavior in whatever package ships that policy, recognized generically by `DefaultOutcomeStatusMapper` via `ITimeoutFailureCase`.

This ticket splits into two halves of very different cost, triaged separately (see Comments):

### Done: generic mapper recognition

`ITimeoutFailureCase` itself already existed as of issue 08 - `Timeout` implements it - but `DefaultOutcomeStatusMapper` didn't yet recognize the interface generically, only the exact `Timeout` type. That gap is now closed: `DefaultOutcomeStatusMapper.Map<TFailure>` has an `ITimeoutFailureCase` branch, ordered after the exact `Timeout` branch, mapping to 408 Request Timeout with the message verbatim (no `Budget`/`Elapsed` fallback, since the interface only guarantees `Message`). This is shape-agnostic (invents no properties) and purely additive, so it needed no driving second implementation - it exists so that a consuming project's *own* `ITimeoutPolicy` implementation, with its own case type implementing `ITimeoutFailureCase`, maps correctly the moment it exists.

- [x] `DefaultOutcomeStatusMapper` has a protected virtual `MapTimeoutFailureCase(ITimeoutFailureCase)` method, ordered after the exact `Timeout` branch in `Map<TFailure>`
- [x] A hand-rolled `ITimeoutFailureCase` implementer (distinct from `Timeout`) maps to 408 with its message
- [x] The exact `Timeout` branch's mapping is unchanged (proven by a test asserting byte-for-byte identical output before and after)
- [x] `PublicAPI.Unshipped.txt` updated for the new protected virtual method
- [x] `dotnet build` and `dotnet test` are green solution-wide

### Still needs-triage: a concrete second implementation

**Do not implement without explicit maintainer sign-off - there is no second concrete implementation driving this today.** `Interlocutor.Abstractions` ships exactly one `ITimeoutPolicy`/`TimeoutBehavior` pair; there is nothing to be agnostic *between* yet, and any policy-context/tag shape would be invented rather than validated against a real API - a real risk to the very "avoid a future breaking change" goal this fidelity work serves, since a wrong guess is itself a future break. If a developer wants this, follow the pattern in `maintainer_docs/adr/0020-validation-failure-case-fidelity.md` and issues 01-03 of `.scratch/validation-failure-fidelity/`, once a real driver names the actual shape.
