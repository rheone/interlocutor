# 11 - `Forbidden` concrete-second-implementation: settle the case-type shape

Status: needs-triage

## Labels

needs-triage

## What this is

Ticket 07's "concrete second implementation" half is parked pending a real `IPolicyEvaluator` implementation
to design against. Before that implementation exists, a throwaway prototype sanity-checked a candidate
`IForbiddenFailureCase` shape against four scenarios - see [Prototype](#prototype) below. This ticket holds
the findings so they aren't lost, and stays `needs-triage` itself: no implementation exists yet, so nothing
here should move to `ready-for-agent` until a maintainer decision names one.

## Candidate shape validated

```csharp
public readonly record struct SomePolicyEvaluatorFailure(
    string Reason,
    IReadOnlyList<DeniedPolicy> DeniedPolicies,
    IReadOnlyList<string> EvaluationOrder) : IForbiddenFailureCase;

public readonly record struct DeniedPolicy(string Name, string Reason);
```

**Held up well:** `DeniedPolicies` was populated in every scenario (single denial, two policies denying for
the same reason, two policies denying for genuinely different reasons, a short-circuited evaluation) and is
the one field that visibly beats today's plain `Reason` string - the "two policies, different reasons"
scenario is a case where the current shape actively loses information a caller might want.

**An open gap the prototype's own scenarios couldn't resolve:** every scenario modeled a fail-fast evaluator,
so `EvaluationOrder` came out identical to `DeniedPolicies` in every single run. That means these four
scenarios never actually tested whether `EvaluationOrder` earns its place as a field distinct from
`DeniedPolicies`, or is redundant restating the same order. Resolving this needs either:

- A fifth scenario modeling an evaluator that checks **all** configured policies (not fail-fast) where at
  least one passes and at least one fails - only then would `EvaluationOrder` diverge from `DeniedPolicies`
  and show its own value, or confirm it doesn't have any; or
- A direct answer from whoever builds the real `IPolicyEvaluator`: does it check every policy, or stop at
  first denial? That alone would settle whether `EvaluationOrder` is worth keeping.

**Also flagged:** the short-circuit scenario (evaluator configured with two policies, only the first ever
runs) raises whether `EvaluationOrder` should mean "policies actually evaluated" or "policies configured" -
those read very differently to a caller and the field name doesn't currently disambiguate.

**No illegal-construction scenario found for this domain** - unlike RateLimited's fail-open and Timeout's
handled fallback, every `Forbidden`-shaped scenario tried genuinely was a denial. Worth confirming this holds
for whatever real evaluator gets built, but it's not a gap in the prototype itself.

## Still needed before this can move past needs-triage

1. A **named, real** `IPolicyEvaluator` implementation (e.g. one that checks and reports multiple named
   policies) that a maintainer commits to building - per ticket 07 and ADR-0020's "Extension-point
   consistency" rationale.
2. Whether that implementation is fail-fast or exhaustive - this single fact resolves the `EvaluationOrder`
   question above without needing further prototyping.
