# 05 - `RateLimited` failure-case fidelity

Status: split - generic mapper recognition done; concrete second implementation remains needs-triage

## Labels

done, needs-triage

A specific `IRateLimiter` implementation - a distributed/Redis-backed limiter, a token-bucket algorithm with its own diagnostic shape - might want to expose more than the generic `RateLimited` struct's `LimitKey`/`RetryAfter`/`Message` (e.g. bucket size, tokens remaining, window boundaries). The same treatment given to validation in this feature (issues 01-04) would apply cleanly here: a technology-specific case type and companion behavior in whatever package ships that limiter, recognized generically by `DefaultOutcomeStatusMapper` via `IRateLimitedFailureCase`.

This ticket splits into two halves of very different cost, triaged separately (see Comments):

### Done: generic mapper recognition

`IRateLimitedFailureCase` itself already existed as of issue 08 - `RateLimited` implements it - but `DefaultOutcomeStatusMapper` didn't yet recognize the interface generically, only the exact `RateLimited` type. That gap is now closed: `DefaultOutcomeStatusMapper.Map<TFailure>` has an `IRateLimitedFailureCase` branch, ordered after the exact `RateLimited` branch, mapping to 429 Too Many Requests with the message verbatim. This is shape-agnostic (invents no properties) and purely additive, so it needed no driving second implementation - it exists so that a consuming project's *own* `IRateLimiter` implementation, with its own case type implementing `IRateLimitedFailureCase`, maps correctly the moment it exists.

- [x] `DefaultOutcomeStatusMapper` has a protected virtual `MapRateLimitedFailureCase(IRateLimitedFailureCase)` method, ordered after the exact `RateLimited` branch in `Map<TFailure>`
- [x] A hand-rolled `IRateLimitedFailureCase` implementer (distinct from `RateLimited`) maps to 429 with its message
- [x] The exact `RateLimited` branch's mapping is unchanged (proven by a test asserting byte-for-byte identical output before and after)
- [x] `PublicAPI.Unshipped.txt` updated for the new protected virtual method
- [x] `dotnet build` and `dotnet test` are green solution-wide

### Still needs-triage: a concrete second implementation

**Do not implement without explicit maintainer sign-off - there is no second concrete implementation driving this today.** `Interlocutor.Abstractions` ships exactly one `IRateLimiter`/`RateLimitedBehavior` pair; there is nothing to be agnostic *between* yet, and any property shape (bucket size, tokens remaining, window boundaries) would be invented rather than validated against a real API - a real risk to the very "avoid a future breaking change" goal this fidelity work serves, since a wrong guess is itself a future break. If a developer wants this, follow the pattern in `maintainer_docs/adr/0020-validation-failure-case-fidelity.md` and issues 01-03 of `.scratch/validation-failure-fidelity/`, once a real driver names the actual shape.
