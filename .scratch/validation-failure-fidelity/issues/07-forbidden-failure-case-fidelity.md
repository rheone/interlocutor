# 07 - `Forbidden` failure-case fidelity

Status: split - generic mapper recognition done; concrete second implementation remains needs-triage

## Labels

done, needs-triage

A specific `IPolicyEvaluator` implementation might want to expose which policy (or policies) denied a request and why, beyond the generic `Forbidden` struct's plain `Reason` string. The same treatment given to validation in this feature (issues 01-04) would apply cleanly here: an evaluator-specific case type and companion behavior wherever that evaluator ships, recognized generically by `DefaultOutcomeStatusMapper` via `IForbiddenFailureCase`.

This ticket splits into two halves of very different cost, triaged separately (see Comments):

### Done: generic mapper recognition

`IForbiddenFailureCase` itself already existed as of issue 08 - `Forbidden` implements it - but `DefaultOutcomeStatusMapper` didn't yet recognize the interface generically, only the exact `Forbidden` type. That gap is now closed: `DefaultOutcomeStatusMapper.Map<TFailure>` has an `IForbiddenFailureCase` branch, ordered after the exact `Forbidden` branch, mapping to 403 Forbidden with no body (consistent with `Forbidden`'s own reason-is-never-exposed design). This is shape-agnostic (invents no properties) and purely additive, so it needed no driving second implementation - it exists so that a consuming project's *own* `IPolicyEvaluator` implementation, with its own case type implementing `IForbiddenFailureCase`, maps correctly the moment it exists.

- [x] `DefaultOutcomeStatusMapper` has a protected virtual `MapForbiddenFailureCase(IForbiddenFailureCase)` method, ordered after the exact `Forbidden` branch in `Map<TFailure>`
- [x] A hand-rolled `IForbiddenFailureCase` implementer (distinct from `Forbidden`) maps to 403 with no body
- [x] The exact `Forbidden` branch's mapping is unchanged (proven by a test asserting byte-for-byte identical output before and after)
- [x] `PublicAPI.Unshipped.txt` updated for the new protected virtual method
- [x] `dotnet build` and `dotnet test` are green solution-wide

### Still needs-triage: a concrete second implementation

**Do not implement without explicit maintainer sign-off - there is no second concrete implementation driving this today.** `Interlocutor.Abstractions` ships exactly one `IPolicyEvaluator`/`AuthorizationBehavior` pair; there is nothing to be agnostic *between* yet, and any denial-detail shape (which policy failed, multiple policies) would be invented rather than validated against a real API - a real risk to the very "avoid a future breaking change" goal this fidelity work serves, since a wrong guess is itself a future break. If a developer wants this, follow the pattern in `maintainer_docs/adr/0020-validation-failure-case-fidelity.md` and issues 01-03 of `.scratch/validation-failure-fidelity/`, once a real driver names the actual shape.
