# 10 - `Timeout` concrete-second-implementation: settle the case-type shape

Status: needs-triage

## Labels

## What this is

Ticket 06's "concrete second implementation" half is parked pending a real `ITimeoutPolicy` implementation to
design against. Before that implementation exists, a throwaway prototype sanity-checked a candidate
`ITimeoutFailureCase` shape against four scenarios - see [Prototype](#prototype) below. This ticket holds
the findings so they aren't lost, and stays `needs-triage` itself: no implementation exists yet, so nothing
here should move to `ready-for-agent` until a maintainer decision names one.

## Candidate shape validated

```csharp
public readonly record struct SomeTimeoutPolicyFailure(
    string Budget,
    string Elapsed,
    string Message,
    string TimeoutSource,      // "inner-call" | "pipeline-budget"
    string? PolicyKey,
    string? ExecutionStrategy) : ITimeoutFailureCase;
```

**Held up well:** `TimeoutSource` and `PolicyKey` were populated and meaningfully different across every
non-illegal scenario (an inner HTTP call timing out vs. the pipeline's own overall budget expiring vs. a
retry-wrapped inner timeout) - worth keeping.

**Needs a maintainer decision, not just a shape tweak:** the retry-wrapped scenario (a retry policy wraps the
timeout policy; the 3rd attempt times out) exposed that `Elapsed` is genuinely ambiguous once retries are
involved - does it mean *this attempt's* elapsed time, or the *whole retry loop's*? Two live options:

- **(a)** Document `Elapsed` as always meaning this attempt only; cumulative time across retries is the
  caller's own problem to compute (e.g. from its own logging/tracing).
- **(b)** Split into two fields, `AttemptElapsed` and `TotalElapsed`.

**Also flagged:** `ExecutionStrategy` degraded to a meaningless `"n/a"` placeholder on the pipeline-budget
path (there's no inner Polly strategy to name at that layer) - a real implementation should make this
nullable rather than stringly-typed "not applicable."

**A scenario that should never reach this case at all:** a Polly fallback policy catching the timeout and
returning a cached value - that's a handled success, not a `Timeout` failure. No field fixes this; it's a
control-flow requirement on the real `ITimeoutPolicy`/`TimeoutBehavior` integration, not a shape gap.

## Still needed before this can move past needs-triage

1. A **named, real** `ITimeoutPolicy` implementation (e.g. Polly-backed) that a maintainer commits to
   building - per ticket 06 and ADR-0020's "Extension-point consistency" rationale.
2. A maintainer call on the `Elapsed` ambiguity above (option a vs. b) - this is a real design decision,
   not something the prototype can settle on its own.
