## What this is

Ticket 05's "concrete second implementation" half is parked pending a real `IRateLimiter` implementation to
design against. Before that implementation exists, a throwaway prototype sanity-checked a candidate
`IRateLimitedFailureCase` shape against four scenarios - see [Prototype](#prototype) below. This ticket holds
the findings so they aren't lost, and stays `needs-triage` itself: no implementation exists yet, so nothing
here should move to `ready-for-agent` until a maintainer decision names one.

## Candidate shape validated

```csharp
public readonly record struct SomeRateLimiterFailure(
    string LimitKey,
    int? RetryAfterSeconds,
    string Message,
    int BucketCapacity,
    int TokensRemaining,
    DateTimeOffset? WindowResetAt,
    string Algorithm) : IRateLimitedFailureCase;
```

**Held up well:** `BucketCapacity`, `TokensRemaining`, `Algorithm` were populated in every non-illegal
scenario fired (burst, sustained abuse, clock skew) - strong candidates to ship as required, non-nullable
fields.

**Needed to change:** `RetryAfterSeconds` and `WindowResetAt` went null under a clock-skew scenario (the
limiter's clock disagrees with the app server's, so a confident retry-after/reset time can't be computed).
Both need to be nullable rather than just non-negative - a caller needs to be able to tell "unknown" apart
from "retry immediately."

**A scenario that should never reach this case at all:** Redis dropping mid-check and the limiter failing
open. No field fixes this - it's not a shape gap, it's a control-flow requirement on whichever concrete
`IRateLimiter` gets built: the fail-open path must return success, never construct this failure case.
Whoever picks this ticket up should carry that requirement into the real implementation's own ticket/tests.
