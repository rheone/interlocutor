Problem: ADR-0015 narrowed InterlocutorBuilder's pipeline surface, but the validation engine it gained under ADR-0014 — ComputeProblems and its three reflection-based checks — regrew the type to 675 lines; the module is shallow again on a different axis.

Solution: Move ComputeProblems and its supporting reads into a dedicated validator module that operates over the accumulated registration list; ValidateOnBuild() stays a one-line forward, same as InterlocutorBuilder.Pipeline does today for pipeline composition.

  • Locality: validation bugs concentrate in one module, not tangled with accumulation
  • InterlocutorBuilderTests.cs splits the same way InterlocutorPipelineBuilderTests.cs already did
  • Interface shrinks; implementation absorbs the checks
Extends, doesn't contradict, ADR-0014 (validation stays registration-list-only) and the intent behind ADR-0015 (narrow InterlocutorBuilder's job) — just applies that same cut to the axis ADR-0015 didn't touch.

Problem: ADR-0014 gave both adapters one shared RegistrationReport — the data stopped duplicating. The order it's applied in (handlers → generated → stages → stage factories → behaviors → matched rules → defaults → root-scope wiring) and the three lifetime-switch translators (Apply/ApplyFactories/TryApplyDefaults) are still hand-copied across two files, kept in sync only by matching comments.

Solution: Pull the seven-step ordering into a container-neutral driver that each adapter feeds three small per-registration callbacks (add-handler, add-factory, try-add-default) — the seam two adapters already justify by existing.

  • Leverage: one ordering, N adapters (a third container costs three callbacks, not a re-derived sequence)
  • Deletion test passes: removing the duplicated code today would force reconstructing it from the sibling file
  • Six near-identical lifetime switches collapse to one

Problem: the file already extracts real analysis into HandlerTypeAnalyzer, GenericUsageAnalyzer, OpenGenericHandlerResolver, and NotificationHandlerOrderPlanner — each independently callable and tested. Three more algorithms (missing/duplicate/catch-all handler detection, ~120 of the file's 348 lines) don't follow that pattern; they're private statics reachable only through the full incremental pipeline.

Solution: lift the three Report* methods into a sibling analyzer type, called from Execute the same way HandlerTypeAnalyzer.Analyze is.

  • Locality: the codebase's own pattern applied consistently
  • Tests hit one interface instead of driving the whole generator pipeline

Collapse Mediator's three tracing wrappers into one

Worth exploring in-process

src/Interlocutor.Abstractions/Mediator.cs:155-182, 213-235, 570-591

Before — 3 bands, same skeleton

TraceSendAsync — tag, try/catch, SetStatus
TraceDispatchAsync — same skeleton
TracePublishAsync — same skeleton, no outcome tag

After — 1 band

TraceAsync<T>(tag outcome?) — one skeleton, 3 call sites

Problem: TraceSendAsync, TraceDispatchAsync, and TracePublishAsync repeat the identical 5-step control-flow skeleton (start Activity, tag request type, try/dispatch/tag outcome, catch/SetStatus/rethrow); a fix to the catch handling needs three edits by hand, in the file the commit history already flags as hottest.

Solution: one generic tracing helper parameterized over whether the dispatch produces a taggable IOperationOutcome; three call sites feed it.

  • Locality: one skeleton to fix, not three
  • Same fix applies to the smaller sibling duplication in SequentialNotificationHandlerWrapper / ParallelNotificationHandlerWrapper's shared preamble

Top recommendation
