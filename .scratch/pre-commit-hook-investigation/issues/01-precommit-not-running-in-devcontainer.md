# 01 - Investigate pre-commit hook not running in this dev environment

Status: ready-for-agent

## Labels

ready-for-agent

## What to build

`git commit` in this devcontainer prints `` `pre-commit` not found.  Did you forget to activate your virtualenv? `` and silently skips every hook in `.pre-commit-config.yaml` (the line-ending/EOF/trailing-whitespace fixers, `check-yaml`, `check-merge-conflict`, `check-added-large-files`, `markdownlint`, `codespell`, `dotnet-format-style`, `gitleaks`) instead of running them. Two contributing facts, found in `.git/hooks/pre-commit` (generated by the `pre-commit` framework, not tracked by git):

- The generated hook's templated `INSTALL_PYTHON` points at a Windows path (`C:\Users\...\AppData\Local\Programs\Python\Python39\python.exe`) that doesn't exist on this Linux/WSL devcontainer.
- Its fallback, `command -v pre-commit`, also fails - the `pre-commit` CLI isn't installed or on `PATH` in this container.
- The hook has been locally patched to `exit 0` unconditionally, specifically so a missing `pre-commit` install never blocks a commit. The practical effect today is that every configured hook - including `gitleaks` secret scanning and `dotnet-format-style` - is silently skipped in this environment, not merely non-blocking on failure.

Investigate whether this container is meant to run `pre-commit` at all (and if so, provision it - e.g. via devcontainer setup, `pip install pre-commit` + `pre-commit install`, or an equivalent), or whether these checks are meant to be covered by CI instead when committing from a container like this one. Confirm whether CI independently enforces any of these same checks, so the gap - if this container is never meant to run them locally - doesn't quietly rely on a human always committing from a machine where `pre-commit` happens to already be installed.

## Acceptance criteria

- [ ] Root cause documented: why `pre-commit` isn't available in this devcontainer (missing install vs. wrong path vs. never provisioned)
- [ ] Determine whether CI independently enforces the same checks (`dotnet-format-style`, `gitleaks`, `markdownlint`, `codespell`, the universal file-normalization hooks) - if not, flag that as a separate gap rather than silently accepting it
- [ ] Either: `pre-commit` is installed and working for commits made from this devcontainer (hooks actually run, not just fail open), or there's a documented decision that this environment intentionally relies on CI instead
- [ ] If provisioning is added, it's captured somewhere a future container rebuild won't lose it (devcontainer config, setup script, or a README/CONTRIBUTING note) - not just a manual one-off install
- [ ] No change to the hook's fail-open behavior (`exit 0`) without explicit confirmation that's still wanted - it was deliberately patched that way
