# 03 - Spike: should `InterlocutorPipelineBuilder`'s `Add*Behavior` methods be table-driven?

**What to build:** Not a rewrite - a written decision. `InterlocutorPipelineBuilder.cs:254-471` (`src/Interlocutor.DependencyInjection.Abstractions/`) has six `Add*Behavior` methods (`AddLoggingBehavior`, `AddAuditingBehavior`, `AddAuthorizationBehavior`, `AddCancellationBehavior`, `AddTimeoutBehavior`, `AddRateLimitedBehavior`) sharing an `AddBehavior` + N×`TryAddDefault` shape, which looks collapsible into one loop over a small descriptor table. But each method's XML doc comment carries behavior-specific rationale (e.g. why `AddLoggingBehavior` deliberately registers no `IResponseOutcomeDescriber` default, per ADR-0009's no-orphan-dependency reasoning), and this exact area already went through a deepening pass recorded in ADR-0014 (DI builder matching registration and build validation) and ADR-0015 (pipeline composition behind `InterlocutorPipelineBuilder`), which rejected alternatives including a per-handler-type lifetime map. Read both ADRs, then produce a short written recommendation: collapse (with a design for carrying each method's rationale as descriptor metadata, not losing it), or leave as-is (with the reason). If the recommendation is "collapse," file a follow-up implementation ticket - do not implement in this ticket.

**Blocked by:** None - can start immediately.

**Status:** done

## Comments

**Decision: collapse the shared body only, not the public method surface.** Add a small private `BehaviorDescriptor` (behavior type + an array of `(serviceType, implementationType)` default-dependency pairs) and one private `AddFromDescriptor(BehaviorDescriptor)` helper doing exactly what the six method bodies already do (`this.AddBehavior(descriptor.BehaviorType)` then a `TryAddDefault` per dependency pair, then `return this`). Each of the six public methods (`AddLoggingBehavior`, `AddAuditingBehavior`, `AddAuthorizationBehavior`, `AddCancellationBehavior`, `AddTimeoutBehavior`, `AddRateLimitedBehavior`) keeps its own name, its own full XML doc comment verbatim, and its own `<see cref>`-linked descriptor field - it becomes a one-line expression body (`=> this.AddFromDescriptor(LoggingDescriptor);` etc.) instead of 1-6 lines of `AddBehavior`/`TryAddDefault` calls. `AddValidationBehavior` and `AddUnitOfWorkBehavior` are explicitly out of scope, matching how this ticket itself scoped the candidate list to six: both do conditional reflective type-probing across optional packages, skip-reporting, and (for `AddUnitOfWorkBehavior`) EF-Core-vs-NHibernate arity-mismatch handling that doesn't reduce to a `(type, defaults[])` shape without losing real logic, not just prose.

**Rationale preservation:** untouched. The XML doc comment - including `AddLoggingBehavior`'s ADR-0009 no-orphan-dependency remarks and `AddAuditingBehavior`'s cross-reference to it, and the "no prescribed position in the pipeline" remark shared by `AddCancellationBehavior`/`AddTimeoutBehavior`/`AddRateLimitedBehavior` - stays exactly where a reader already looks for it: on the still-distinct public method. The descriptor itself carries zero prose, only `(Type, (Type, Type)[])` data, so there is nothing for a "descriptor metadata" design to lose.

**ADR alignment:** consistent with both. ADR-0015's decision is about *which type* owns pipeline composition (`InterlocutorPipelineBuilder`, reachable via `.Pipeline`) and keeping one copy of each method's documentation - this change doesn't touch the public surface, method count, or naming ADR-0015 established; it only shares the six methods' identical *implementation* bodies, which is exactly the "one canonical write path" spirit ADR-0015 already applied to `SetDefault`. ADR-0014's rejected "per-handler-type lifetime map" is a different shape of collapse - it would have replaced an explicit `AddHandler` call with an *implicit* table consulted during a bulk scan, collapsing caller-visible behavior into configuration data. This decision does the opposite: every call site still explicitly calls a named `Add*Behavior` method; only the repeated procedural body behind six *already-explicit* calls is shared.
