# pre-commit in the Devcontainer: Root Cause and Provisioning Decision

**Status:** decision taken and implemented. Investigated and resolved against
[`.scratch/pre-commit-hook-investigation/issues/01-precommit-not-running-in-devcontainer.md`](../.scratch/pre-commit-hook-investigation/issues/01-precommit-not-running-in-devcontainer.md).

## Symptom

Every `git commit` made from this devcontainer printed:

```
`pre-commit` not found.  Did you forget to activate your virtualenv?
```

...and the commit proceeded anyway - every hook in `.pre-commit-config.yaml`
(the file-hygiene fixers, `markdownlint`, `codespell`, `dotnet-format-style`,
`gitleaks`) was silently skipped rather than run.

## Root cause

`.git/hooks/pre-commit` is generated by the `pre-commit` framework itself and
is **not tracked by git** - it lives only in the working tree. Two things
about the existing generated hook combine to produce the symptom:

1. Its templated `INSTALL_PYTHON` path was baked in wherever `pre-commit
   install` was last run against this working copy, and points at a
   Windows path (`C:\Users\...\AppData\Local\Programs\Python\Python39\python.exe`)
   that does not exist inside this Linux/WSL devcontainer.
2. Its fallback, `command -v pre-commit`, also failed, because nothing in
   `.devcontainer/` ever installed the `pre-commit` CLI into the container.
   The devcontainer installs a Python runtime
   (`ghcr.io/devcontainers/features/python:1`, which also brings `pipx`) but
   `post-create.sh` stopped short of installing `pre-commit` itself or
   running `pre-commit install`.

So this was never a "wrong path that used to work" regression - `pre-commit`
was never provisioned in the devcontainer in the first place. The hook has
also been locally patched to `exit 0` unconditionally regardless of which
branch above fires, specifically so a missing install never blocks a commit;
that patch is intentional and independent of the root cause above (see
[Fail-open behavior, unchanged](#fail-open-behavior-unchanged)).

## Does CI cover the same checks?

No. `.github/workflows/ci.yml` runs `dotnet restore`/`build`/`test`, a trim-
analyzer gate, and `dotnet csharpier check . --syntax-errors-as-warnings`.
None of that overlaps with what `.pre-commit-config.yaml` configures:

| `.pre-commit-config.yaml` hook | Covered by CI? |
| --- | --- |
| `mixed-line-ending`, `end-of-file-fixer`, `trailing-whitespace` | No |
| `check-yaml`, `check-merge-conflict`, `check-added-large-files` | No |
| `markdownlint` | No |
| `codespell` | No |
| `dotnet-format-style` (`dotnet format style --include`) | No - CI's `dotnet csharpier check` is a different tool (layout/whitespace) from `dotnet format style` (naming/modifiers/IDE-analyzer preferences); CI does not run the latter at all |
| `gitleaks` (secret scanning) | **No** |

Nothing here was double-covered by CI. In particular, **`gitleaks` secret
scanning has no CI equivalent at all** - a commit made from a container where
`pre-commit` silently fails open is the only place that check would have run,
and it wasn't running. This made provisioning `pre-commit` properly in the
devcontainer the right call rather than documenting the gap and moving on:
the gap was real, not redundant with CI.

## What changed

[`post-create.sh`](../.devcontainer/post-create.sh) now installs the
`pre-commit` CLI via `pipx install pre-commit` (`pipx` ships with the
`ghcr.io/devcontainers/features/python:1` feature already declared in
[`devcontainer.json`](../.devcontainer/devcontainer.json), so no new feature
was needed) whenever `pre-commit` isn't already on `PATH`. This runs on every
container create, so it survives a rebuild.

Deliberately **not** done: running `pre-commit install` to regenerate
`.git/hooks/pre-commit`. That would overwrite the existing hook file, and
with it the fail-open `exit 0` patch described below. Installing only the CLI
is sufficient: the existing hook's second branch (`elif command -v
pre-commit`) starts succeeding once `pre-commit` is on `PATH`, so hooks now
actually run and their auto-fixers actually fix files in place - without
touching the hook file at all.

Verified in this container: after `pipx install pre-commit`, running the
hook directly against staged files exercises every configured hook (`pre-
commit run --files <path>` showed the file-hygiene fixers, `codespell`, and
`dotnet-format-style` all executing instead of reporting "no files to
check").

## Fail-open behavior: unchanged, flagged for a maintainer decision

The hook's trailing `exit 0` - unconditional, regardless of whether any
hook fails - was left exactly as it was found. It was deliberately patched
in previously, is outside what this investigation was asked to change, and
this note does not take a position on whether it should stay that way long
term.

What is now true, that wasn't before: hooks in this container actually run
and actually report failures to the terminal, they just still cannot block
the commit. Before this fix, the practical effect of fail-open and "pre-
commit isn't even invoked" were identical (both let every commit through
silently); after this fix they're no longer identical - a failing `gitleaks`
or `codespell` result is now visible output at commit time, not silence. A
maintainer may want to revisit whether `exit 0` should still apply
unconditionally now that hooks are actually running, particularly for
`gitleaks`, given CI doesn't cover it either - but that's a decision for a
human to make deliberately, not one this change makes on its own.
