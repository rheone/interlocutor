# ADR-0023: Pipeline Behavior Case Construction Fails Fast, Never Degrades or Reshapes

**Status:** Accepted

## Context

`AuthorizationBehavior`, `CancellationBehavior`, `TimeoutBehavior`, `RateLimitedBehavior`, `ValidationBehavior`, and `FluentValidationErrorsBehavior` are all generic over `TResponse : IUnion` - the constraint [ADR-0013](0013-response-constrained-to-outcome-no-streaming.md) established for every query/command response type - deliberately unconstrained beyond that - each behavior's own XML doc remarks, and [ADR-0020](0020-validation-failure-case-fidelity.md)'s rejected "decompose `TResponse` into a fixed failure-case generic parameter" alternative, already explain why: Microsoft.Extensions.DependencyInjection's open-generic resolver requires an implementation to declare exactly as many open type parameters as the service interface it's paired against (`IPipelineBehavior<TRequest, TResponse>`, arity 2), so a third open parameter pinning the failure case can't be added behind that two-parameter contract.

Because `TResponse` can't be pinned at compile time, each of the six behaviors short-circuits by constructing the specific case it needs - `Forbidden`, `Cancelled`, a timeout case, `RateLimited`, `ValidationErrors`, `FluentValidationErrors` - reflectively via `IOutcomeCaseRegistry`, through the shared `OutcomeCaseRegistryExtensions.ConstructOrThrow` helper. When a handler's chosen `TResponse` union doesn't declare the case a behavior attached to its request needs, `ConstructOrThrow` catches the registry's `OutcomeCaseNotSupportedException` and re-throws a behavior-named `InvalidOperationException` describing the mismatch. This is already the shipped runtime behavior, and it is already correct - but two things about it were unrecorded and one was untested:

- Nothing stated, as a design decision rather than an implementation detail six call sites happen to share, that this fail-fast contract is deliberate and permanent - that a behavior which can't construct its case must never fall back to a silent `null`/unset `Outcome`, and must never force or reshape a case into a `TResponse` that doesn't declare it.
- The signal only fires the first time a real request actually triggers the mismatch (the first genuine denial for a request implementing `IRequiresPolicyRequest` paired with a `TResponse` lacking `Forbidden`, for example) - a configuration mistake that can sit undetected until it happens to occur in production traffic, with nothing checking for it earlier.
- `TimeoutBehavior` was the one behavior of the six with no test proving its fail-fast path actually works (closed separately by `.scratch/pipeline-case-fidelity/issues/01-timeoutbehavior-no-case-test.md`, commit `5070da0`).

Separately, nothing recorded *why* a handler's response arity is chosen the way it is - specifically, that it is never legitimate to add a case to a response union, or swap in a differently-shaped union, merely because some pipeline behavior wired up alongside the handler happens to need that case. `Outcome<...>` arity/case selection ([ADR-0001](0001-use-csharp-15-unions-for-result-types.md)) is a per-handler decision about what that handler's domain operation can actually produce; a pipeline behavior is cross-cutting infrastructure a request opts into via a marker interface ([ADR-0004](0004-marker-interfaces-for-cross-cutting.md)), registered independently of any given handler ([ADR-0009](0009-no-default-pipeline.md)'s flat, builder-composed list). Letting the second dictate the first would mean a handler's public response contract drifts based on which behaviors a particular deployment happens to wire in - the same kind of implicit, hard-to-audit coupling ADR-0009 rejected for pipeline composition itself, now at the level of a handler's own signature.

## Decision

### Fail fast; never degrade to a silent outcome; never reshape `TResponse`

A pipeline behavior that cannot construct the case it needs from a handler's `TResponse` **must** fail fast with a named `InvalidOperationException` identifying the behavior, what it was trying to do, and what response shape would have worked - never silently return a default/unset `Outcome`, and never force or coerce a case into a `TResponse` that doesn't declare it. This is now a documented convention, not merely an emergent property of `ConstructOrThrow`'s existing implementation: `AuthorizationBehavior<TRequest, TResponse>` (`Forbidden`), `CancellationBehavior<TRequest, TResponse>` (`Cancelled`), `TimeoutBehavior<TRequest, TResponse>` (`Timeout`), `RateLimitedBehavior<TRequest, TResponse>` (`RateLimited`), `ValidationBehavior<TRequest, TResponse>` (`ValidationErrors`), and `FluentValidationErrorsBehavior<TRequest, TResponse>` (`FluentValidationErrors`) all route through `OutcomeCaseRegistryExtensions.ConstructOrThrow`, which catches `IOutcomeCaseRegistry.Construct`'s `OutcomeCaseNotSupportedException` and re-throws it as a behavior-named `InvalidOperationException`. Any future behavior with the same shape - constructing a specific outcome case from an unconstrained `TResponse : IUnion` - must call `ConstructOrThrow` (or an equivalent that upholds the same three guarantees) rather than inventing its own fallback.

### A handler's response arity is a domain decision, never behavior-dictated

Which cases a handler's `Outcome<...>` (or hand-rolled `IUnion`) response declares is chosen by what that handler's own operation can actually produce - not by which pipeline behaviors happen to be registered against requests of that type. A request implementing `IRequiresPolicyRequest`, `ICancellableRequest`, `IRateLimitedRequest`, or `ITimeoutRequest` is declaring only that the corresponding cross-cutting concern applies to it; it is not thereby obligated to add `Forbidden`, `Cancelled`, a timeout case, or `RateLimited` to its response shape as a matter of course. A handler whose domain genuinely cannot be denied, cancelled, rate-limited, or timed out in a way worth reporting to its caller is entitled to a response union that doesn't carry that case - the cost is that the corresponding behavior throws if that assumption turns out to be wrong (the request is paired with the marker interface but not the matching case), which is exactly the fail-fast guarantee above, not a reason to force the case in anyway. This is the same reasoning [ADR-0009](0009-no-default-pipeline.md) already applies to pipeline composition itself (nothing runs on a request unless the request opts in) turned around: opting a request into a behavior via a marker interface does not retroactively reach back into the handler's own response-type declaration.

### The compile-time analyzer is an earlier-feedback layer on top of the same runtime guarantee, not a replacement for it

A separate, later ticket (`.scratch/pipeline-case-fidelity/issues/03-generator-analyzer-case-fidelity-diagnostic.md`) adds a new `Interlocutor.Generator` diagnostic (`INTERLOC012`) that flags a mismatched `(TRequest, TResponse)` pair at build time, for consumers using compile-time handler discovery ([ADR-0008](0008-compile-time-handler-discovery.md)). It is deliberately implemented without touching `TResponse`'s type, `IOutcomeCaseRegistry`'s contract, or how any container resolves these behaviors - it is pure static analysis over already-discovered handler pairs, reading what the generator already knows about `TRequest`'s implemented interfaces and `TResponse`'s declared cases, exactly the "earliest-feasible compile-time signal... without changing `TResponse`'s shape, `IOutcomeCaseRegistry`'s contract, or how any container resolves these behaviors" scope the PRD for this effort commits to. The runtime `InvalidOperationException` this ADR requires remains the backstop regardless: the analyzer catches a mismatch earlier for the consumer who has it available, but every mismatch it can catch is also, unconditionally, caught at runtime the first time it's actually triggered.

### Analyzer scope: the four marker-interface-gated behaviors only

The analyzer's scope is `AuthorizationBehavior`, `CancellationBehavior`, `RateLimitedBehavior`, and `TimeoutBehavior` - gated respectively by `IRequiresPolicyRequest`, `ICancellableRequest`, `IRateLimitedRequest`, and `ITimeoutRequest` (the current marker-interface names, per `Interlocutor.Abstractions.Markers`, after the rename tracked separately in `.scratch/marker-interface-naming/`). `ValidationBehavior` and `FluentValidationErrorsBehavior` are deliberately **not** in scope: neither is gated by a marker interface on `TRequest` at all - both run for every request and short-circuit at runtime based on whether at least one `FluentValidation.IValidator<TRequest>` is actually registered in the built container. Whether a validator is registered is a DI-registration fact, invisible to a compile-time analyzer working only from `TRequest`'s and `TResponse`'s declared shape - the same request type can be paired with zero validators in one composition root and several in another, with nothing in either type's declaration telling them apart. Those two behaviors stay covered by the runtime throw this ADR requires, plus a later ticket's (`.scratch/pipeline-case-fidelity/issues/06-startup-validation-case-fidelity.md`) opt-in startup-validation extension, which - unlike the analyzer - runs against a built `IServiceProvider` and can see which validators are actually registered.

### Open question: equivalent compile-time coverage for a consumer's own marker interface

This ADR does not resolve whether a consumer who defines their own marker interface and their own behavior (the extension pattern [ADR-0004](0004-marker-interfaces-for-cross-cutting.md) and [ADR-0020](0020-validation-failure-case-fidelity.md)'s "Extension-point consistency" section both establish as first-class) should get equivalent compile-time coverage, or whether `INTERLOC012` stays permanently hardcoded to the four shipped markers. A plausible mechanism - an attribute a consumer places on their own marker interface or behavior, naming the case type the analyzer should require - is not designed here. This is recorded deliberately as an open scope question, not a silent gap: a consumer's custom marker/behavior pair is fully covered by this ADR's runtime fail-fast guarantee regardless of how this question is eventually resolved: only the *earliness* of the feedback (build time vs. first real trigger) is what's left open, not the guarantee against a silent or reshaped outcome.

## Consequences

- **Positive:** The fail-fast/never-degrade/never-reshape rule is now a stated convention that governs any future behavior with this shape, not just an implementation detail of six existing call sites that happened to agree with each other.
- **Positive:** A handler's response arity stays a pure domain decision, auditable from the handler's own declared `Outcome<...>` without needing to cross-reference which behaviors are registered against it in a given composition root.
- **Positive:** The compile-time analyzer, once `.scratch/pipeline-case-fidelity/issues/03-generator-analyzer-case-fidelity-diagnostic.md` lands, gives consumers on the compile-time discovery path a build-time signal for the four marker-gated behaviors, without any change to `TResponse`, `IOutcomeCaseRegistry`, or DI resolution.
- **Negative:** Until issue 03 lands, every consumer's earliest signal for any of the six behaviors is still the runtime exception on first trigger; until issue 06 lands, the reflection/`ScanAssembly` discovery path (per [ADR-0008](0008-compile-time-handler-discovery.md)) has no earlier-than-runtime signal at all, for any of the six.
- **Negative:** `ValidationBehavior`/`FluentValidationErrorsBehavior` never get a compile-time diagnostic under this design, by construction - only the DI-registration-time and runtime layers can see the fact the analyzer would need.
- **Negative:** A consumer's own custom marker interface and behavior get no compile-time coverage today, and whether they ever will remains an open question this ADR explicitly declines to settle.

## Alternatives considered

- **A static-abstract-interface constraint (`IConstructibleFrom<TResponse, TCase>`) forcing every response arity to prove at compile time it can hold every case any attached behavior might need.** Rejected - this inverts the domain-decision principle above: it would force a handler's `TResponse` to satisfy a constraint shaped by whichever behaviors happen to be wired into its pipeline, rather than letting the handler's own domain need drive its response shape. A handler with no legitimate `Forbidden` case would either be forced to add one it doesn't need, or forced to avoid `IRequiresPolicyRequest`/`AuthorizationBehavior` altogether even where authorization is otherwise wanted - both worse than a behavior that fails loudly at the one call site where the mismatch is real.
- **Letting an unconstructible case resolve to a null/unset `Outcome` instead of throwing.** Rejected - this breaks the exhaustiveness guarantee `Match`/`Switch`/a compiler-checked `switch` are built on ([ADR-0001](0001-use-csharp-15-unions-for-result-types.md)). A caller pattern-matching over every case `TResponse` declares would either miss a case that's silently never populated, or have to add a defensive default arm to cover a "no case is actually active" state the type system says can't happen - turning a loud, named, developer-facing exception into a silent non-value that erodes the exact guarantee the union-typed result model exists to provide.
