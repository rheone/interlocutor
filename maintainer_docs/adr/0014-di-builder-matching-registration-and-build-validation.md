# ADR-0014: DI Builder Extension - Explicit Handler Lifetime, Type-Matching Registration, and Opt-In Build Validation

**Status:** Accepted

## Context

`InterlocutorBuilder`'s handler discovery today is a single fixed policy: `ScanAssembly` and its siblings register every discovered handler at a hardcoded `Scoped` lifetime, with no way to register one handler manually at a different lifetime without bypassing the builder entirely. A consumer who wants to register services by some other criterion than "implements a known handler contract interface" - a naming convention, a custom attribute, an arbitrary predicate over the type - has no first-class way to do it through `InterlocutorBuilder`; they'd have to reflect over assemblies themselves and call the underlying `IServiceCollection`/`ContainerBuilder` directly, losing the builder's container-neutrality and everything downstream that depends on registrations flowing through it.

Separately, the builder validates almost nothing at configuration time - only `ArgumentNullException` guards exist. A scanned request type with no registered handler, two registrations of the same service/implementation pair at conflicting lifetimes, or a registration rule that was expected to match something but silently matched nothing, are all discoverable only by resolving a handler and watching it fail (or in the missing-handler case, not automatically at all - see the existing, separate, opt-in `ValidateHandlerRegistrations`). And there is no single place to see what the builder actually accumulated and why: debugging "why isn't X registered" or "why did X get registered twice" means reading every builder call site by hand.

## Decision

- **Explicit, overridable lifetime on the scan methods.** `ScanAssembly`, `ScanAssemblies`, `ScanAssemblyContaining<TMarker>`, and `ScanEntryAssembly` each gain an added `RegistrationLifetime lifetime = RegistrationLifetime.Scoped` parameter. The default reproduces today's exact behavior; nothing changes for a caller who doesn't pass it. This is chosen over a second, differently-named "bare bones" method because bare-bones handler registration was never actually different from today's behavior - only the lifetime was hardcoded rather than exposed - so there is nothing left to name separately.
- **A manual handler escape hatch: `AddHandler(Type, RegistrationLifetime)`.** Mirrors `AddBehavior`'s existing shape, including open-generic support. This is the outlet for the one case a bulk scan call can't express on its own: one specific handler at a lifetime different from the rest of a scanned batch. An explicit `AddHandler` call for a type takes precedence over an incidental duplicate discovered by scanning the same assembly - deliberate intent expressed through a direct call outranks a type that merely happened to be swept up by a broad scan.
- **Type-matching registration, additive to marker-interface filtering, not a replacement for it.** A new mechanism lets a consumer register a rule - a predicate over candidate types found while scanning, with support for excluding specific matches from a broader rule - that registers every type it matches as a handler and/or as a pipeline behavior. This is a different shape from the one existing predicate-based mechanism in the codebase, `OutcomeClassifierBuilder.RegisterPredicate`: that one tests a single runtime value against many predicates and takes the first match (fail-closed on no match), because it's answering "what is this one value." A registration match rule is answering the reverse question - "which of these many candidate types qualify" - so it tests one rule against many types and applies its action to every match, not just the first. It does not touch or replace marker-interface-based behavior scoping (`ITransactionalRequest`, `IAuditableRequest`, `IRequiresPolicy`, `IExternalStoreRequest`): that remains the one mechanism for "which requests does a given behavior touch," decided independently and left untouched here. Matching a rule against zero types is legal and silent by default - a rule can opt into requiring at least one match, in which case an unmet requirement is a build-validation failure rather than a silent no-op.
- **`ValidateOnBuild()`: opt-in, and answerable from the registration list alone.** Chained onto the builder, it checks only what the accumulated registration list can prove without a live container: every request type found while scanning has a matching handler registration, every match rule marked as required actually matched something, and no two registrations of the same (service type, implementation type) pair disagree on lifetime. It does not attempt anything that requires a built provider (an unresolvable constructor dependency, for instance) - that class of check remains the job of the existing, separate, still-opt-in `ValidateHandlerRegistrations(IServiceProvider, assemblies)`, unchanged. Keeping `ValidateOnBuild()` to registration-list-only checks is what keeps it container-neutral and synchronous, avoiding a framework-specific startup hook (`IHostedService`, `IStartupFilter`, or equivalent) that would tie it to one container. All problems `ValidateOnBuild()` finds are aggregated into a single dedicated exception, raised once with everything wrong rather than one failure at a time across repeated build-fail-fix cycles.
- **One shared report model, not two.** A single internal model - registered entries with their provenance (explicit call, scan discovery, or matched rule), what was skipped and why (an optional-package soft dependency that wasn't found, a match rule that found nothing), and any problems found - is built every time `AddInterlocutor` runs. `DescribeRegistrations()` exposes it for inspection at any time, with a structured form and a human-readable formatter over it; the Microsoft and Autofac packages may each optionally pipe it through `ILogger` where one is available. `ValidateOnBuild()`'s exception carries this same object rather than a second, separately-built structure - the debugging report and the validation failure are two ways of consuming one set of facts, not two facts kept in sync by hand. This is also how the existing silent optional-package probing (`TryGetType`, used to conditionally wire `Interlocutor.FluentValidation`/`Interlocutor.EntityFrameworkCore`/`Interlocutor.NHibernate` support only when referenced) becomes visible without becoming an error: a skip the report will show, not a failure `ValidateOnBuild()` raises.

## Consequences

- **Positive:** A consumer who wants a non-default handler lifetime, a single manually-registered handler, or convention-based registration by an arbitrary predicate no longer has to bypass `InterlocutorBuilder` and lose container-neutrality to get it.
- **Positive:** Configuration mistakes that are knowable before a container is even built - a missing handler, a required match that found nothing, a lifetime disagreement between two registrations of the same pair - surface as one aggregated, actionable exception instead of being discovered one dispatch at a time.
- **Positive:** "What did the builder actually register, and why" has one answer, inspectable on demand, rather than requiring a manual read of every builder call site.
- **Positive:** The previously-invisible optional-package soft-dependency skip becomes visible without becoming a new failure mode - it was deliberately silent before and stays silent, just no longer opaque.
- **Negative:** The registration list now needs to track provenance per entry (which call or rule produced it), a small bookkeeping cost on every registration path, in exchange for the report and the lifetime-conflict check being possible at all.
- **Negative:** Two ways to register a handler manually now exist for the same job at different granularity - `AddHandler` for one type, a match rule for many. Accepted: they answer different questions ("this one, explicitly" vs. "everything matching this shape"), and collapsing them into one API would force the single-type case to express itself as a trivial predicate for no real benefit.

## Alternatives considered

- **A per-handler-type lifetime map inside a single scan call**, instead of a separate `AddHandler` escape hatch: rejected - it would complicate the common bulk-scan path to serve an exception case, when a separate explicit call already exists as a pattern (`AddBehavior`) for exactly this kind of one-off override.
- **Reusing `OutcomeClassifierBuilder`'s first-match-wins, fail-closed predicate algorithm** for type-matching registration: rejected - it answers a different cardinality of question (one value against many predicates) than registration matching does (one rule against many candidate types), and forcing the same algorithm shape onto both would make the fail-closed default meaningless here (unmatched types aren't a failure; they're simply not part of that rule).
- **Automatic, non-opt-in validation at `AddInterlocutor` time**: rejected - this library's registration surface deliberately runs nothing the consumer didn't explicitly ask for (see [ADR-0009](0009-no-default-pipeline.md)), and the same reasoning that removed the legacy `InterlocutorOptions` type and its implicit defaults applies here - validation that runs whether or not you asked for it is exactly the kind of ambient behavior this library has already rejected once.
- **A `ValidateOnBuild()` that resolves against a live container**: rejected - it would require building a real provider before `AddInterlocutor` can return, forcing a framework-specific startup hook per container and breaking the container-neutral design every other part of the builder maintains. The existing, separate `ValidateHandlerRegistrations(IServiceProvider)` already covers checks that genuinely need a live container; `ValidateOnBuild()` covers what doesn't.
- **Two separate models for the debugging report and the validation-failure payload**: rejected - both describe the same underlying facts (what got registered, what didn't, and why); building and maintaining them independently would only risk them drifting out of sync with each other.
