# ADR-0015: Pipeline Composition Lives Behind `InterlocutorBuilder.Pipeline`, Not On `InterlocutorBuilder` Itself

**Status:** Accepted

## Context

`InterlocutorBuilder` was, by commit-churn count, the hottest file in the codebase's recent history. Ticket 40 responded by extracting pipeline-composition state - the behavior list, the stage list, the stage-factory list, and the try-add-able defaults dictionary those pipeline behaviors depend on - into a dedicated `InterlocutorPipelineBuilder`, constructed internally and shared through `InterlocutorBuilder`'s constructor. At the time, ticket 40 kept the public surface unchanged: every pipeline method (`AddBehavior`, the named `Add*Behavior` convenience methods, `UseRecommendedChain`, the `AddStage`/`AddStageHost` family) stayed on `InterlocutorBuilder` as a one-line forward to the identically-named method on the new inner type, each carrying its own near-verbatim copy of the XML doc comment.

That move shifted state sideways without deepening either type. `InterlocutorBuilder`'s public interface stayed exactly as wide as `InterlocutorPipelineBuilder`'s - every pipeline method existed on both, so a reader had no way to tell from the type alone which one owned "what runs in what order" versus "which assemblies get scanned." The documentation burden doubled instead of shrinking: every pipeline method's XML doc comment existed in two places, and `InterlocutorBuilderTests.cs` and `InterlocutorPipelineBuilderTests.cs` both asserted the same forwarding behavior (order, duplicates, try-add precedence) at two seams instead of one.

A second, smaller inconsistency compounded this: `OverrideAuditSink`/`OverridePolicyEvaluator`/`OverrideOutcomeDescriber` wrote to the shared defaults dictionary through `InterlocutorBuilder`'s own private `SetDefault`, while `OverrideTimeoutPolicy`/`OverrideRateLimiter`/`OverrideOutcomeCaseRegistry` already delegated through `InterlocutorPipelineBuilder`'s independently-implemented copy of the same method. Both wrote to the same dictionary instance, so behavior was correct, but having two writers for the identical mechanism was the same shallowness surfacing as an inconsistency rather than as prose duplication.

## Decision

`InterlocutorBuilder.Pipeline` (a new, get-only property returning `InterlocutorPipelineBuilder`) becomes the sole entry point for pipeline composition. `InterlocutorBuilder` drops every mutating pipeline method it previously forwarded - `AddBehavior`, the named `Add*Behavior` convenience methods, `UseRecommendedChain`, the `AddStage`/`AddStageHost` family, and the behavior-dependency `Override*` methods (`OverrideAuditSink`, `OverridePolicyEvaluator`, `OverrideOutcomeDescriber`) - all of which now live exclusively on `InterlocutorPipelineBuilder`, reachable only via `.Pipeline`. `InterlocutorPipelineBuilder` becomes the one deep module for "what runs in what order," carrying the one copy of the doc comment for each method and the one canonical write path (`SetDefault`, now `internal` rather than `private`) to the shared defaults dictionary.

`InterlocutorBuilder` keeps, unchanged: `ScanAssembly`/`ScanAssemblies`/`ScanAssemblyContaining<TMarker>`/`ScanEntryAssembly`, `AddHandler`, `AddTypeMatch`, `AddGeneratedRegistrations`, `ValidateOnBuild`, `DescribeRegistrations`, and the `Behaviors`/`Stages`/`StageFactories`/`Handlers`/`MatchedRegistrations`/`Defaults`/`AssembliesToScan`/`GeneratedRegistrations` read-only projections. `Behaviors`/`Stages`/`StageFactories` stay on `InterlocutorBuilder` as pass-through properties rather than moving behind `.Pipeline` too: they were already single-line forwards, consumed directly by `ServiceCollectionExtensions.cs` (Microsoft) and `ContainerBuilderExtensions.cs` (Autofac), and were never the duplication cost this decision targets - moving them would buy no depth and cost edits in two more packages plus their test projects for no benefit.

`OverrideRequestContextAccessor` is the one exception kept directly on `InterlocutorBuilder`: `IRequestContextAccessor` is ambient infrastructure seeded in the constructor independent of which (if any) pipeline behaviors are configured, not a dependency of a specific pipeline behavior the way the other five `Override*` methods are. It now writes through `InterlocutorPipelineBuilder.SetDefault` (made `internal` for this purpose) rather than keeping its own private copy of the same mechanism.

This is a deliberate breaking change to the public builder surface, consistent with this project's pre-1.0, no-shims norm - the same norm that led ticket 04 to delete the legacy registration API outright rather than deprecating it forward. It reverses ticket 40's explicit "the public surface shown above is unchanged" promise, which existed only as a `documentation/builder-and-registration.md` `[!NOTE]` callout and in code comments, never as its own ADR.

## Consequences

- **Positive:** `InterlocutorBuilder`'s own interface is now visibly narrower than `InterlocutorPipelineBuilder`'s - a reader can tell from the type alone which concern a method belongs to, without reading its doc comment.
- **Positive:** Every pipeline method's documentation exists in exactly one place. `InterlocutorBuilderTests.cs` no longer duplicates `InterlocutorPipelineBuilderTests.cs`'s behavioral assertions (order, duplicates, try-add precedence) - it now only smoke-tests `.Pipeline`'s presence and reference stability, leaving the full behavioral matrix solely on `InterlocutorPipelineBuilderTests.cs`.
- **Positive:** Every `Override*` method that targets a pipeline-behavior dependency writes through the same canonical `SetDefault` path; `InterlocutorBuilder`'s own duplicate copy is gone.
- **Negative:** Every existing call site that used the pre-move surface (`builder.AddBehavior(...)`, `builder.UseRecommendedChain()`, `builder.OverrideAuditSink<T>()`, and so on) must change to `builder.Pipeline.AddBehavior(...)` and equivalents - a mechanical but solution-wide edit across `README.md`, six `documentation/` files, and every DI package's integration test suite.
- **Negative:** A consumer chaining a `Scan*`/`AddHandler`/`AddTypeMatch` call with a pipeline call in one fluent expression now needs an explicit `.Pipeline` hop mid-chain (for example, `builder.ScanAssembly(asm).Pipeline.AddLoggingBehavior()`), rather than the flat single-type chain ticket 40 preserved. Accepted: the alternative was keeping two owners for the same interface indefinitely.

## Alternatives considered

- **Leave the ticket-40 forwarding shape in place indefinitely**: rejected - the doubled documentation and duplicated test matrix are an ongoing maintenance cost that only grows as more pipeline methods are added (ticket 40 already predates `AddCancellationBehavior`, `AddTimeoutBehavior`, and `AddRateLimitedBehavior`, each of which had to be added to both types).
- **Move `Behaviors`/`Stages`/`StageFactories`/`Defaults`/`GeneratedRegistrations` behind `.Pipeline` too, for full symmetry**: rejected - these are read-only projections already consumed directly by both container packages; moving them costs edits in packages and tests this decision has no other reason to touch, for a symmetry argument with no duplication cost behind it.
- **Deprecate the old methods forward with `[Obsolete]` instead of a breaking removal**: rejected - inconsistent with this project's established pre-1.0 norm (ticket 04) of removing a superseded API outright rather than carrying a shim, and an `[Obsolete]` forwarder would still need to exist on both types, defeating the point of this change.
