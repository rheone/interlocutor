# Bootstrap a new project

This is the workflow for creating a brand-new .NET library repo from scratch.
`apply_plan.py` executes a generated JSON plan; always dry-run first and show
the plan to the user before passing `--execute`.

## 1. Gather inputs

Ask the user directly -- don't guess:

- **Library name** (PascalCase, becomes the namespace, assembly name, and
  NuGet package ID unless they say otherwise)
- **License** (MIT / Apache-2.0 / BSD-3-Clause / proprietary / other)
- **Target framework(s)** -- single (`net9.0`) or multi-target
  (`net8.0;net9.0`). Multi-targeting changes `Directory.Build.props` and
  test/benchmark project setup.
- **Test framework** (xUnit / NUnit / MSTest)
- **Which optional components** to include from the manifest groups:
  `benchmarks`, `smoketests`, `husky`, `pre_commit`, `agent_files`,
  `multi_project`. A small internal utility library doesn't need
  BenchmarkDotNet or CODE_OF_CONDUCT -- offer, don't default to "all."
- **GitHub org/repo name** and **author/maintainer name** (used in badges,
  CODEOWNERS, RepositoryUrl, contact emails)
- **SDK version** for `global.json` -- run `dotnet --list-sdks`; don't
  hardcode a guessed version.
- **Packages** -- consult [PACKAGES.md](PACKAGES.md). Ask which of the
  recommended analyzers, test utilities, and quality-of-life packages to add.

## 2. Generate real .NET artifacts via the SDK

`.slnx`, `.csproj`, and `packages.lock.json` are never templated -- they're
generated by the `dotnet` CLI. Build a plan with `"action": "run"` steps:

```
dotnet new slnx -n {{LibraryName}}
dotnet new classlib -n {{LibraryName}} -o src/{{LibraryName}} -f {{TargetFrameworks}}
dotnet new <xunit|nunit|mstest> -n {{LibraryName}}.Tests -o src/{{LibraryName}}.Tests
dotnet sln add src/{{LibraryName}}/{{LibraryName}}.csproj src/{{LibraryName}}.Tests/{{LibraryName}}.Tests.csproj
dotnet add src/{{LibraryName}}.Tests/{{LibraryName}}.Tests.csproj reference src/{{LibraryName}}/{{LibraryName}}.csproj
```

Add benchmarks (console + BenchmarkDotNet package) and abstractions the same
way, only if those groups were selected. After projects exist, run
`dotnet restore --use-lock-file` from `src/` to generate `packages.lock.json`
per project.

## 3. Layer templated files on top

Build `"create_from_template"` actions for every manifest entry with a
non-null `template` and whose `group` matches the selected set. Pass a single
`vars.json` so every template substitutes consistently:
`apply_plan.py --vars-file vars.json`.

## 4. Verify

Run `dotnet build` and `dotnet test` from `src/`. A bootstrap that doesn't
compile is worse than no bootstrap. Fix and re-run before handing off.

## 5. Git init (ask first)

If the user wants version control: `git init`, add `.gitignore` before the
first `git add -A` (order matters -- don't stage `bin/`/`obj/`), then commit.

See [GH-CLI.md](GH-CLI.md) for setting up the GitHub remote after init.
